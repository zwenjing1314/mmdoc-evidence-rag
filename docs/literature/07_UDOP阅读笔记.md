Unifying Vision, Text, and Layout for Universal Document Processing

# 1. 要统一解决哪些文档任务

它的核心野心是将整个 Document AI 领域的任务**统一建模为“序列到序列（Seq2Seq）”的生成问题**。

具体来说，它统一解决了以下两大类、多种具体的文档任务：

**1. 文档理解任务 (Document Understanding)** 这是绝大多数文档模型（如 LayoutLM 系列）的主阵地，UDOP 同样覆盖：

- **文档问答 (Document Question Answering):** 给定一张文档图片和一个问题（如“发票总额是多少？”），模型直接生成答案（如 DocVQA 任务）。
- **信息抽取 (Information Extraction):** 识别和提取表单、收据中的关键键值对（Key-Value pairs）或实体（如 FUNSD、CORD 数据集）。
- **文档分类 (Document Classification):** 根据文档的视觉和文本特征，将其分类为特定的类型（如简历、发票、备忘录等）。

**2. 文档生成任务 (Document Generation)** 这是 UDOP 最大的亮点，也是它区别于纯 Encoder 判别式模型（如 LayoutLMv3）的关键所在。因为使用了 Encoder-Decoder 架构，它能够完成：

- **布局生成 (Layout Generation):** 让模型预测或重建文档的排版结构。
- **跨语言文档翻译等生成式任务:** 直接在理解原文档视觉和布局的基础上，生成翻译后的文本序列。

**核心洞察：** 在 Figure 1 中，你可以看到一个非常关键的设计：UDOP 解决所有这些任务，用的都是**同一个网络骨干**和**同一种输出形式**。它通过在输入端加入**任务提示词（Task Prompt）**（比如输入 "Question answering: What is the date?"），然后让解码器（Decoder）统一**生成**文本结果或坐标标记。

这与你正在研究的 ColPali（输出排序分数进行检索）在任务目标上有本质的差异，但它为了达成这个宏大目标所构建的多模态融合底座，正是我们需要深挖的重点。

# 2. 输入包含哪些信息

正如 UDOP 的标题（Unifying Vision, Text, and Layout）所宣示的那样，它的输入直接且贪婪地包含了文档的**三大核心模态**。

为了实现 Seq2Seq 的大一统，UDOP 在输入端做了一个非常精妙的设计，将这三种异构信息映射到了同一个空间中。具体包含以下三部分：

### 1. Text（OCR 文本序列）

- **来源：** 依赖现成的 OCR 引擎提取文档页面上的所有文字。
- **处理方式：** 像处理标准自然语言一样，把这些 OCR 提取出的单词经过分词器（Tokenizer）转换成 subword tokens（子词序列）。

### 2. Layout（二维布局坐标）

这是 UDOP 非常值得你关注的重点，因为它处理坐标的方式和 LayoutLM 系列不同。

- **来源：** 同样来自 OCR 引擎输出的每个词对应的包围盒（Bounding Box）。
- **处理方式（离散化表示）：** UDOP 没有像以前的模型那样用连续的浮点数做位置编码，而是将坐标归一化到 [0,999] 的区间内，然后**将其转化为了离散的词表 token**。
- 也就是说，一个坐标 [xmin,ymin,xmax,ymax] 会被直接当成四个特殊的“单词”（如 `<loc_120>`）放入序列中。它与对应的 Text token 紧密绑定，共同参与计算。

### 3. Vision（视觉图像）

- **来源：** 原始的文档页面截图。
- **处理方式：** 借鉴了 ViT（Vision Transformer）的做法，将文档图像切分成固定大小的 Image Patches（图像块），然后通过线性投影映射为视觉向量（Visual tokens）。

> **给你的研究提示（联系 ColPali）：**
>
> - **ColPali 的世界里**：输入端只有 Vision（Image Patches），文本 query 是后来在检索阶段才引入做相似度计算的。
> - **UDOP 的世界里**：在模型的最底层输入阶段，就把 **“文本 token + 离散坐标 token + 图像 patch”**全部揉成了一个超长的多模态序列，一起送进统一的编码器。
>
> 这种将**连续坐标离散化为 token** 的思想，对于你未来设计“区域级视觉-文本表示”非常具有启发性。它可以让模型像处理普通文字一样，用自注意力机制（Self-Attention）去学习“位置”与“内容”的关系。

# 3. 它是 Encoder-only 还是 Encoder-Decoder

UDOP 是一个标准的 **Encoder-Decoder（编码器-解码器）** 架构。

这正是它与 LayoutLMv3（典型的 Encoder-only 架构）在网络结构上的**最大分水岭**。我们可以从这两个架构解决任务的思路来看看为什么 UDOP 必须这么选：

- **Encoder-only (如 LayoutLMv3)：** 它的强项是做“理解”和“特征提取”。它把输入的图像、文本和布局编码成稠密的特征向量，如果要做下游任务，必须在最顶层**外接各种特定的任务头 (Task-specific heads)**。比如，做分类就接个线性层，做实体抽取就接个序列标注头（CRF），任务与任务之间是割裂的。
- **Encoder-Decoder (如 UDOP)：** 它不仅继承了 Encoder 的多模态融合能力，更关键的是引入了 **Decoder**。这就允许模型把所有的判别任务、抽取任务全部转化为大一统的“序列到序列 (Seq2Seq) 生成任务”。

**对应到你的研究课题：** 你之前研究的 ColPali 和 MMDocIR 主要是用来做检索的，检索本质上需要的是高质量的**特征向量**用来计算相似度（MaxSim），所以纯 Encoder 往往就足够了。而 UDOP 加上 Decoder，是为了完成更复杂的生成类任务。

这也就直接引出了你阅读方案里第一部分的最后一个问题：**既然它是 Encoder-Decoder 架构，那它的输出到底是向量、类别、抽取结果还是什么呢？**

# 4. 输出形式

UDOP 的最终输出**全部都是文本序列（确切地说，是文本 Token 和布局 Token 的混合序列）**。它既不是纯粹的向量，也不是传统的类别标签，更不是 BIO 这种序列标注的索引。

既然一切都被统一成了 Seq2Seq 的生成任务，Decoder 就像是一个“打字机”，它只能往外“敲”词表里的词（包括我们上一轮聊过的 `<loc_xxx>` 这样的特殊坐标词）。

我们来看看它怎么用“敲字”来覆盖你提到的这几种输出形式：

- **如果任务是分类 (Classification)：** 它不会像传统模型那样输出一个类别 ID 或者 One-hot 向量，而是**直接生成类别的名字**。比如，如果这是一张发票，Decoder 就直接逐个字母生成单词 `I-n-v-o-i-c-e`。
- **如果任务是信息抽取 (Extraction)：** 它不需要在原文本上做复杂的起止位置标注，而是直接**把抽取的实体“默写”出来**。比如，提示词让它抽取“公司名称”，它就直接生成 `Apple Inc.`。
- **如果是带有布局的任务 (Layout Generation/Detection)：** 它会生成坐标加文本。比如生成：`<loc_200> <loc_250> <loc_300> <loc_350> Total Due`。

> **⚠️ 对你课题的至关重要的提醒（划重点！）：**
>
> 你现在的研究目标是做**检索**（借鉴 ColPali 的 MaxSim 机制和 MMDocIR 的思路）。检索的核心是需要计算 Query 和 Page/Region 之间的相似度，这就需要模型输出**稠密特征向量（Dense Vectors）**。
>
> - UDOP 的 **Decoder** 是为了“生成文本”而生的，它的最终输出经过 Softmax 后变成了词，这对于你的高速向量检索来说**毫无用处**，而且推理极慢。
> - **你的“淘宝区”在 UDOP 的 Encoder 端！** UDOP 的 Encoder 将“图像 patch + OCR 文本 + Bbox 坐标”完美融合后，输出的那一层**多模态上下文向量**，正是你想要提取出来做区域级 (Region-level) 匹配的极佳素材。

到这里，你阅读计划里第一部分（摘要和引言）的四个核心问题已经全部闭环了！你的那条流程线非常准确：**输入三模态 -> 统一 Encoder -> Decoder -> 统一生成文本结果**。

接下来，我们就该进入这篇论文的核心地带——二、精读模型架构（重点看 Encoder 里的跨模态融合机制）了。



# 5. 模型架构

UDOP 在多模态融合的设计上，采用的是最直接、也最暴力的**早期融合（Early Fusion）\**和\**单流架构（Single-stream）**。

简单来说，图像、文本和布局坐标，在进入统一编码器（Unified Encoder）的**第一层**就已经被拼接在了一起，并在随后的**每一层**中都通过自注意力机制（Self-Attention）进行深度的全连接交互。

按照你的阅读方案，我们可以把这个过程拆解成两张逻辑图和三个步骤来看。

### 1. 模态的初始特征化 (Embedding)

在进入 Transformer 之前，UDOP 先把不同模态的数据转化为维度相同的特征向量：

- **文本与布局 (Text & Layout)：** 正如我们上一轮聊过的，UDOP 将归一化后的 Bbox 坐标变成了离散的 `<loc_xxx>` token。在输入时，文本词汇和它对应的坐标词汇是紧密排列的。 它们通过同一个 Embedding 层，加上一维的位置编码（1D Position Embedding），转化为**文本-布局特征序列**。
- **图像 (Vision)：** 文档图片被切割成固定的图像块（Image Patches，类似 ViT 的做法）。然后通过一个线性投影层（Linear Projection），并加上二维的位置编码（2D Position Embedding），转化为**视觉特征序列**。

### 2. 序列拼接：The Grand Concatenation

这是最关键的一步。UDOP 没有设计复杂的门控机制或跨模态注意力模块（Cross-Attention）来做融合，而是直接在序列维度上做**物理拼接**。

它把上述两个序列“头尾相连”，变成一个超长的一维多模态序列： `[Text & Layout Tokens, Image Patches]`

### 3. 多模态编码器 (Unified Encoder) 融合

这个超长的拼接序列被直接送入多模态 Transformer Encoder。 在这个 Encoder 的**每一层**中，自注意力机制（Self-Attention）都在全局计算权重。这意味着：

- 图像 Patch 在提取特征时，不仅能看到周围的图像块，还能“读懂”它上面印着的 OCR 文本和对应的坐标信息。
- 文本 Token 在理解语义时，也会“看”向图像中对应的视觉特征。
- 文本、布局和视觉在这一个统一的网络结构中完成了完全的交互，直到 Encoder 的最后一层，输出包含全局上下文的多模态向量。

### 核心架构梳理图

根据你的阅读方案，我们可以把它的架构提炼为这个流程

```
[文本 Token] + [离散 Bbox Token] ──> Embedding ──┐
                                               │
                                               ├─> (Concat 拼接成超长序列) ─> 统一多模态 Encoder ─> T5 Decoder ─> 任务输出
                                               │                              (每层都在深度融合)
[图像 Patch] + [2D 位置编码] ──> Linear Projection ─┘
```

**关于检索场景的思考：**

UDOP 的这种“把所有东西拼成一个超长序列做全局 Attention”的做法，在理解和生成任务上效果极好，因为它让模态间毫无保留地交互。

但如果你要把这种思想搬到 **ColPali 这样的检索模型**中，就需要极度警惕**计算复杂度**。全局 Attention 的计算量是 O(N2)，把成百上千的图像 Patch 和长篇的 OCR 文本拼在一起做 Self-Attention，推理速度会极其缓慢，很难用于大规模索引。

**你的破局点在于“局部性”：** 你不需要让所有的文本都去和所有的 Patch 计算注意力。你可以借鉴它的布局绑定思想，只将**特定 Bbox 内的 OCR 文本与对应的图像 Patch 进行局部融合（区域级视觉-文本表示）**，这样既保留了多模态对齐的优势，又能维持 MaxSim 检索所需的高效特征输出。

# 6. 预训练任务

UDOP 之所以能在理解和生成任务上通吃，核心就在于它的预训练任务设计。它把自监督学习玩出了花样，巧妙地让模型学会了“看图、读字、找位置”。



按照你的阅读计划，我们以论文原文为准，拆解这四个关键的预训练任务：

### 1. Joint Text-Layout Reconstruction (文本-布局联合重建)

- **输入被遮挡了什么？** 随机遮挡一定比例的文本 Token，并且**同时遮挡**它们对应的 Layout Token（坐标）。

- **预测目标是什么？** Decoder 需要生成被遮住的文本，并紧接着生成它的二维坐标。

- **损失如何计算？** 交叉熵损失 (Cross-Entropy Loss)，监督对象是词表和坐标表里的离散 Token。

  

- **它学习了哪种能力？** 结合全局上下文的推理能力。模型不仅要根据上下文和图片猜出“这里写了什么词”，还要懂排版，猜出“这个词印在什么位置”。

### 2. Layout Modeling (布局建模)

- **输入被遮挡了什么？** 只遮挡部分元素的 Layout Token（坐标），但**保留**其文本 Token。

  

- **预测目标是什么？** Decoder 需要根据给定的文本、上下文和图像，预测这段文本应该出现的位置。

  

- **损失如何计算？** 交叉熵损失，专门监督 Layout 坐标 token `<loc_xxx>`。

- **它学习了哪种能力？** 纯粹的空间结构感知能力。比如它会学到“Title”通常在页面顶端大字号区域，“Total”通常在账单右下角。

### 3. Visual Text Recognition (视觉文本识别)

- **输入被遮挡了什么？** 遮挡文本 Token，但**保留**它的 Layout Token（坐标）。

- **预测目标是什么？** 相当于让模型做一个 OCR 任务——根据给定的坐标框，把那块图像区域里的字给“读”出来。

- **损失如何计算？** 交叉熵损失，监督对象是文本 Token。

  

- **它学习了哪种能力？** **极其关键的细粒度跨模态对齐能力。** 它强迫模型学会把具体的视觉 Patch 特征，和它对应的文字语义在局部区域上严丝合缝地绑定起来。

### 4. Masked Image Reconstruction (掩码图像重建)

- **输入被遮挡了什么？** 遮挡大量的图像 Patch（类似 MAE 机制）。

- **预测目标是什么？** 视觉 Decoder 需要根据未遮挡的图像，以及完整的文本和布局序列，重建出被遮挡区域的原始像素。

  

- **损失如何计算？** 连续像素值的均方误差损失 (MSE / L2 Loss)。

- **它学习了哪种能力？** 底层视觉特征表征，以及文档级的多模态生成能力（模型甚至能根据文字和坐标，把原本那块图给画出来）。

### 这些损失适合你的检索模型吗？

如果你直接把这些生成式损失（交叉熵和 MSE）套用到你的跨模态检索研究里，计算开销极大，而且输出的也不是你想要的稠密特征。

但我们可以吸收其中的核心思想，将它们**改造成检索损失**，特别是结合你之前研究 CLIP 架构时非常熟悉的**对比损失 (Contrastive Loss)** 思路：

**1. 改造“视觉文本识别” -> 区域级对比损失 (Region-level Contrastive Loss)** UDOP 用生成的方式做对齐，你的模型可以更轻量：利用 Bbox 坐标，提取出特定区域的视觉 Patch 向量序列，并与该区域的 OCR 文本向量进行 InfoNCE 对比学习。这能直接为你的区域检索（Query-Region）提供强大的局部视觉-文本联合特征。

**2. 改造“布局建模” -> 位置提示 (Layout Prompting/Embedding)** 你不必让模型去预测坐标，而是可以把 Bbox 归一化后通过 MLP 投影成特征向量，直接作为一种空间维度的 Attention 偏置或 Embedding，注入到对应图像 Patch 的表征里。

**3. 舍弃“掩码图像重建”** 生成像素对于提高检索精度收益极低。如果你需要做区域级的掩码预训练，可以改为预测被 Mask 区域特征向量的余弦相似度，这更符合检索模型拉近正样本距离的诉求。

# 7. 下游任务和实验

进入下游任务与实验分析部分，这正是检验 UDOP “大一统”架构到底有多能打的关键环节。

按照你的阅读方案，我们先把下游任务的整体情况用一张表梳理清楚，然后再直击你最关心的消融实验（Ablation Study）部分。

### 一、 下游任务与实验整理表

UDOP 在实验部分横扫了各大 Document AI 榜单（如 DUE-Benchmark、CORD 等）。它的实验设定可以总结如下：

| 任务类型          | 示例数据集     | 输入是否依赖 OCR 和 Bbox | 输出形式 (Decoder生成) | 评估指标            | 基线模型对比               |
| ----------------- | -------------- | ------------------------ | ---------------------- | ------------------- | -------------------------- |
| **文档问答 (QA)** | DocVQA, WTQ    | **强依赖**               | 纯文本答案序列         | ANLS, EM (精确匹配) | 优于 LayoutLMv3, Donut, T5 |
| **信息抽取 (IE)** | FUNSD, CORD    | **强依赖**               | 实体或键值对的文本序列 | F1 Score            | SOTA，显著优于纯文本模型   |
| **文档分类**      | RVL-CDIP       | **强依赖**               | 类别名称的文本序列     | Accuracy (准确率)   | 优于 LayoutLMv3            |
| **文档生成**      | 论文自定义任务 | 依赖部分提示 (如文本)    | 图像像素 / 布局坐标    | MSE / 坐标准确度    | 首次实现高质量文档联合生成 |

### 二、 核心消融实验解析：去掉模态后会发生什么？

UDOP 的实验和消融分析（Table 4 及周边论述）非常清晰地回答了你列出的那四个关键问题：

**1. 去掉 Layout (布局) 后下降多少？**

- **致命打击：** 如果去掉二维布局坐标（即退化为纯文本的一维序列），在 FUNSD（表单键值对抽取）和 CORD（收据信息抽取）这种高度依赖排版的任务上，性能会出现**断崖式下跌**。
- **原因：** 发票或表单上的文字如果只按从左到右、从上到下的顺序读出，会完全丧失“左右对齐”或“跨列表格”的逻辑关系，导致模型根本找不到 Key 对应的 Value。

**2. 只使用 OCR 文本是否已经足够？**

- **远远不够：** 虽然在一些简单的、纯文本密集的 QA 任务上，纯文本模型（如基础的 T5）能拿到基础分数，但它的上限很低。
- **瓶颈：** 一旦遇到需要结合图表、印章、签名（视觉特征）或复杂多列排版（布局特征）的复杂文档，只吃 OCR 文本的模型就会立刻失效。

**3. 图像信息在哪些任务上真正有帮助？**

- **宏观版式感知：** 在 **RVL-CDIP（文档分类）** 中，图像信息发挥了决定性作用。因为发票、备忘录、简历往往从整体视觉风格上一眼就能区分，图像特征在此类任务中贡献极大。

  

- **底层特征兜底：** 图像 Patch 能作为 OCR 的补充。如果 OCR 引擎把“0”识别成了“O”，模型依然可以通过观察该区域的图像 Patch 提取正确的视觉语义。

- **消融结论：** 论文证明了将视觉特征与文本、布局在同一个 Encoder 中进行**统一的早期融合 (Unified Encoder)**，比把视觉和文本分开编码（Dual-encoder）效果更好。

**4. Encoder-Decoder 是否主要提升了生成任务？**

- **不仅是生成，更是统一：** Encoder-Decoder 确实赋予了 UDOP 独一无二的“文档布局生成”和“掩码图像重建”能力。但更重要的是，这种架构**统一了判别和生成任务**。
- 它让模型彻底摆脱了过去那种“做一个任务就得设计一个专属网络头（Task-specific heads）”的繁琐工程。

> **对你检索课题的启发：**
>
> 消融实验证明，**布局 (Layout) 是连接文本和视觉的绝对桥梁**。 虽然 UDOP 的 Seq2Seq 生成式输出不适合你的检索任务，但它证明了“把 OCR 文本与它对应的局部 Bbox 图像紧密绑定”是极其有效的。在你的研究中，如果能提取这种**区域级 (Region-level) 的多模态融合向量**来做相似度计算，一定会比纯粹依靠视觉 Patch (如原生 ColPali) 或纯粹依靠文本 (如传统 BM25) 强大得多。

# 8. 论文对照

这正是整个阅读计划中最能产生科研火花的一步。将这三篇顶会论文放在一起，就像是在为你的跨模态检索模型挑选最合适的“架构零件”。

它们各自的核心贡献不仅不可替代，而且恰好能拼凑出一条清晰的升级路线：

### 1. LayoutLMv3：多模态表征与判别基石

LayoutLMv3 提供的是“如何做好文档特征提取”的底层标准。

- **不可替代的思路：** 它是纯 Encoder 架构的代表，证明了将文本 Token、图像 Patch 和连续的 Bbox 坐标映射到同一特征空间进行编码，能产生极高质量的稠密特征（Dense Features）。
- **对你的价值：** 它的判别式特征输出，比 UDOP 的生成式输出更契合检索任务的需求。你可以借鉴它的特征融合方式，作为特征提取骨干。

### 2. UDOP：空间布局的深度激活

UDOP 虽然是为 Seq2Seq 生成而生，但它在“深层次绑定模态关系”上做到了极致。

- **不可替代的思路：** 将 2D 坐标离散化为 Layout Token，让位置信息直接参与全局 Self-Attention；同时，其“视觉文本识别”预训练任务强制模型学习了极细粒度的区域级图文对齐。
- **对你的价值：** 它证明了 Bbox 不仅仅是位置偏置，更是连接视觉与文本的桥梁。你可以借鉴这种细粒度对齐的思想，在你的模型中设计区域级（Region-level）的交互机制，而不是仅仅依赖全局文本或全局图像。

### 3. ColPali：高效多向量检索架构

ColPali 解决的是“如何让多模态特征在检索场景下跑得又快又准”的工程与算法难题。

- **不可替代的思路：** 抛弃了传统的单向量（Dense Vector）表征，采用多向量（Multi-vector）表征结合 MaxSim 晚期交互（Late Interaction）机制，完美绕开了长文本 OCR 的计算瓶颈。
- **对你的价值：** 这是你整个检索框架的“底盘”。你的目标不是抛弃 ColPali，而是要在其纯视觉 Patch 的基础上，通过 LayoutLMv3 和 UDOP 的启发，把局部的 OCR 与布局特征“无缝注入”到这些 Patch 向量中。

### 融会贯通：你的下一代检索模型雏形

如果你把这三者的精髓提取出来，你的 MMDocIR 演进方向应该是一套“局部富化的多向量检索架构”：

- **骨架（取自 ColPali）：** 维持多向量特征与 MaxSim 检索机制，保证大规模检索的效率。
- **输入增强（取自 UDOP）：** 不再输入全篇 OCR 干扰注意力机制，而是提取关键实体的 OCR 文本及其 Bbox。
- **区域对齐（取自 LayoutLM/UDOP）：** 在 Encoder 阶段，利用 Bbox 作为锚点，让特定的 OCR 文本向量只与它对应坐标内的图像 Patch 向量进行局部融合，从而生成具备极强语义区分度的“富文本 Patch 向量”。

# 9. 对于课题的启发

UDOP 的统一融合思想，以及 ColPali 的多向量检索架构，针对你的多模态文档检索课题，以下是三个可以直接指导你下一步架构设计的具体启发：

## 1. 布局信息不是普通的“附加文本”，而是跨模态的“物理锚点”

在纯文本模型中，排版是丢失的；在纯视觉模型（如原版 ColPali）中，排版是隐式的。UDOP 和 LayoutLMv3 都向我们证明了一个真理：**Bounding Box 是连接高层语义（文本）和底层像素（视觉）的唯一确定性桥梁。**

- **落地方向：** 在你的改进模型中，千万不要直接把 OCR 文本和图像 Patch 盲目拼接。你可以利用 Bbox 作为“锚点（Anchor）”，让坐标信息参与到多模态表示的计算中。例如，将 Bbox 归一化后映射为空间 Embedding，注入到 ColPali 的视觉 Patch 中，让模型明确感知“这个 Patch 位于页面的标题区还是表格区”。

## 2. 摒弃全局注意力，走向“区域级（Region-level）视觉-文本对齐”

UDOP 能够把庞大的 OCR 序列、离散坐标和图像 Patch 放在一起做全局 Self-Attention，但这在长文档检索（尤其是需要处理上千个 Token 的页面）中会导致计算量爆炸，且不利于生成用于 MaxSim 计算的多向量。

- **落地方向：** 采用一种**轻量级的局部融合策略**。不要让所有的文本和所有的图像 Patch 产生交互。你可以先通过 Bbox 定位（比如一个特定的实体框或段落框），提取该区域的视觉 Patch 序列，再提取该区域对应的 OCR Token。
- **具体做法：** 设计一个浅层的融合模块，只在这两个**局部序列**之间进行特征交互（Region-level Vision-Text Representation）。这样既吸收了 UDOP 跨模态融合的精髓，又保持了 ColPali 级别的检索效率。

## 3. 重塑预训练目标：要判别，不要生成

UDOP 虽然极其强大，但它的损失函数（如文本/坐标生成、像素级图像重建）是为 Seq2Seq 生成任务服务的，直接拿来做检索预训练不仅收敛慢，而且特征鉴别力差。

- **落地方向：** 你的多任务损失需要**非常明确的监督信号**，并且要以“排序（Ranking）”为导向。你可以将 UDOP 的“视觉文本对齐”思路改造成对比学习损失（Contrastive Loss）：
  1. **页面级（Page-level）对比损失：** 确保 Query 能够召回正确的整体文档页面。
  2. **区域级（Region-level）对比损失：** 强迫局部区域的“融合后特征”与 Query 中的细粒度意图（如表格中的某个具体数值）高度对齐。
  3. **可选的图文对齐辅助损失：** 在 Encoder 内部拉近同一个 Bbox 内的视觉特征与 OCR 文本特征的距离。

> **阶段性总结**
>
> 读完这三篇论文，你的知识架构已经非常完整了：
>
> - **LayoutLMv3** 给了你如何把文本、图像、Bbox 融合成高质量稠密特征的**规范**；
> - **UDOP** 拓宽了你的视野，告诉你坐标可以离散化，图文必须在**局部区域严密绑定**；
> - **ColPali** 则是你整个工程的**地基**，它的多向量 MaxSim 机制是你保证检索速度和效果的底牌。
