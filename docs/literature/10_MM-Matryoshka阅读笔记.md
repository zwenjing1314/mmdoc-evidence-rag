# 解决的问题

ColPali 类模型每页存储大量 patch 向量，且需要完整 VLM 前向编码。MM-Matryoshka 通过同时训练不同 Transformer 层和不同向量维度可用的检索表示，使一个模型能够在推理时按预算选择表示大小与编码深度。

它研究两种预算：

```
维度预算 Dimension：
128 维 -> 64 维 -> 32 维
减少每个向量的存储和 MaxSim 点积成本。

层数预算 Layer：
最终层 -> 中间层 -> 更浅层
可通过 early exit 少跑部分 Transformer 层，减少编码成本。
```



它通常不直接减少“每页 patch 个数”，而是压缩每个 patch 的维度、或提前退出编码器。

# MM-Matryoshka 阅读笔记

## 1. 基本信息

- 完整标题：MM-Matryoshka: Towards Budget-Elastic Visual Document Retrieval via a 2D Multimodal Matryoshka Training Framework
- arXiv ID：[arXiv:2606.07654](https://arxiv.org/abs/2606.07654)
- 核心任务：为 ColPali 类视觉文档多向量检索模型提供“二维预算弹性”，使同一个模型可在不同编码层数和向量维度预算下进行检索。
- 基础模型：
  - PaliGemma + ColPali；
  - Qwen2-VL + ColQwen2；
  - Qwen2.5-VL + ColQwen2.5。
- 是否开源代码和权重：论文写明计划向社区发布代码和 checkpoint；截至论文 v1，需到作者主页或仓库进一步确认实际是否已公开。

## 2. 它要解决的问题

- ColPali 类多向量模型的主要成本：
  - 每页保存大量 patch 向量；
  - 每个 patch 向量通常有完整维度，例如 128 维；
  - 文档侧建库时需要完整运行视觉语言模型；
  - 查询和页面的 MaxSim 计算成本随向量维度、patch 数量和候选页面数增加。
- 现有压缩方法的不足：
  - 直接截断 embedding 维度会明显损害检索质量；
  - 只优化向量维度或只减少编码层数，无法统一平衡存储与计算；
  - 为每一种预算分别训练一个模型，训练和部署成本很高。
- MM-Matryoshka 的核心假设：
  - 最终层、完整维度的检索表示包含可嵌套的有效信息；
  - 通过联合训练，可以让较浅层和较低维度的表示也保留较好的检索排序能力；
  - 同一模型可根据设备预算选择 `(layer, dimension)`，而无需为每种预算重新训练模型。

## 3. 输入与输出

- Query 输入：文本 query。
- 页面输入：文档页面图像。
- 文档表示：页面经 VLM 编码后产生 patch 级多向量表示；可从不同 Transformer 层取出，并保留前 `d` 个维度。
- Query 表示：query 经同一检索模型编码为 token 级多向量；需与文档侧使用相同的层和维度预算。
- 输出：页面相关性排序分数，以及不同预算下的检索结果。
- 是否仍使用 MaxSim：是。无论使用完整表示还是压缩表示，仍采用 ColBERT/ColPali 的 MaxSim 晚期交互。

## 4. 2D 可变预算表示

### 层数预算

- 可选层：

  - 最终层；
  - 中间层；
  - 更浅层。

  不同 backbone 的具体层号不同。例如，论文中 PaliGemma 的中间层示例为第 9 层，较浅层示例为第 4 层；Qwen 系列使用与自身深度相适应的层。

- 如何取中间层表示：

  - 在目标 Transformer 层读取 hidden states；
  - 将其变换为可用于检索的 token 向量；
  - 以该层表示替代最终层表示参与 MaxSim。

- 是否支持 early exit：支持。论文说明若实际实现提前退出，则不必执行后续 Transformer 层。

- 对编码时间的影响：

  - 中间层或浅层 early exit 可减少页面和 query 的编码计算；
  - 只有“真正提前停止前向计算”才会带来编码延迟下降；
  - 若仍完整跑到最终层、仅取中间 hidden state，则不会节省完整编码成本。

### 维度预算

- 可选维度：论文主要报告 `128`、`64`、`32` 维预算。
- 如何截断：
  - 从检索向量前缀保留前 `d` 个维度；
  - query 和页面向量必须使用相同的维度前缀。
- 截断后是否归一化：是。论文说明取维度前缀后需要重新进行 L2 归一化，再进行 MaxSim。
- 对存储和 MaxSim 的影响：
  - 单个向量存储从 `128` 维缩减到 `64` 或 `32` 维；
  - 文档索引存储大致随维度线性缩小；
  - MaxSim 点积宽度降低，打分计算成本相应下降；
  - 但 patch 数量本身不减少。

### 2D 预算

- ```
  (layer, dimension)
  ```

   如何定义：

  - `layer`：从哪一层提取检索表示；
  - `dimension`：该表示保留前多少维；
  - 例如 `(final layer, 128)` 是完整预算，`(middle layer, 32)` 是较低预算。

- 训练时覆盖哪些组合：

  - 对一组选定层 `S` 和一组选定维度 `D` 联合训练；
  - 完整组合可写为 `S × D`；
  - 具体可用层集合由 backbone 深度和中间层 hidden state 质量决定。

- 推理时如何选择：

  - 根据存储、编码时间和检索精度预算选择一个 `(layer, dimension)`；
  - 不需要为新预算重新训练模型；
  - 用选定层的 query/page 向量、选定维度前缀和同样的 MaxSim 完成检索。

## 5. 训练目标

| 损失                          | 输入                                                         | 监督目标                               | 作用                             |
| ----------------------------- | ------------------------------------------------------------ | -------------------------------------- | -------------------------------- |
| 完整预算检索损失              | 最终层、完整维度的 query/page 表示                           | 正页面排在负页面之前                   | 保持高预算模型的主检索能力       |
| Prefix 检索损失               | 最终层但不同前缀维度的 query/page 表示                       | 低维前缀也能区分正负页面               | 让 `64`、`32` 等低维表示可用     |
| Layer-wise score distillation | 最终层完整表示的分数分布作为 teacher；中间层/低维表示作为 student | student 的候选页面排序分布接近 teacher | 让浅层和低维表示保留检索排序行为 |
| 联合损失                      | 完整预算损失 + 多个 `(layer, dimension)` 蒸馏项              | 同时优化不同预算                       | 训练一个可弹性部署的模型         |

- 最终层检索损失：
  - 对最终层的不同前缀维度进行检索监督；
  - 论文将这部分记为 `L_prefix`。
- 低维前缀损失：
  - 让低维向量的前缀不是“随意截断后碰巧可用”，而是被显式训练为可检索表示。
- 中间层蒸馏：
  - 使用 KL 散度，使中间层或低维预算下的页面分数分布接近最终层完整表示；
  - teacher 分支采用 stop-gradient；
  - 蒸馏的是候选页面的检索分数分布，而不是强行要求每个 patch 向量完全相同。
- 总损失：
  - `L = L_prefix + λ × 平均(L_distill(layer, dimension))`
  - 其中蒸馏项覆盖训练时选择的 `S × D` 预算组合。
- 训练数据：
  - `vidore/colpali_train_set`。
- 正负样本：
  - 使用 query-positive page 的检索训练设置；
  - 论文主文强调 batch 内候选页面分数分布的蒸馏；
  - 具体 hard negative 构造和 batch 配置应在代码或附录中进一步核对。

## 6. 实验

- 数据集：

  - ViDoRe V1；
  - ViDoRe V2；
  - 论文分别汇总 V1 的 10 个子集和 V2 的 4 个子集。

- 基线：

  - ColPali；
  - ColQwen2；
  - ColQwen2.5；
  - 对应 backbone 的直接 layer/dimension 截断版本。

- 页面检索指标：

  - `nDCG@5` 为主指标；
  - `Recall@1`；
  - `Recall@5`。

- 效率指标：

  - 页面 embedding 索引存储；
  - 页面编码/建库延迟；
  - query 编码延迟；
  - 固定候选集上的 MaxSim 打分时间；
  - 论文采用 bf16 footprint 计算索引大小，即：

  ```
  page token 数 × 选择的向量维度 × 2 bytes
  ```

- 最优预算：

  - 没有对所有 backbone 和所有部署条件都固定的最佳预算；
  - 论文强调根据目标精度、存储和延迟选择不同 `(layer, dimension)`；
  - 中间层 + 低维通常是较有代表性的平衡点。

- 极端压缩预算：

  - 较浅层 + `32` 维是高压缩设置；
  - 这种设置可大幅减少存储和编码计算，但性能会有明显下降。

- 主要结果：

  - MM-Matryoshka 在多数层数/维度压缩预算下，明显优于未经训练就直接截断的 ColPali、ColQwen2 和 ColQwen2.5；
  - 例如，对 PaliGemma/ColPali，直接压缩到中间层 `32` 维时，ViDoRe V1 的表现保留率很低；经 MM-Matryoshka 训练后，仍能保持较高比例的完整预算性能；
  - 论文证明二维联合训练比只做后处理截断更稳定。

- 失败或退化场景：

  - 层越浅、维度越低，性能通常越明显下降；
  - 最激进的“浅层 + 32 维”预算仍显著弱于完整预算；
  - MM-Matryoshka 改善的是压缩后的性能保持，不代表极端压缩没有代价；
  - 它不减少 patch 数量，因此页面 patch 数量很大时，仍存在多向量索引和 MaxSim 的规模问题。

## 7. 与 ColPali 的关系

- 相同点：
  - 都使用视觉文档页面作为文档输入；
  - 都产生页面 patch 多向量；
  - 都产生 query token 多向量；
  - 都使用 MaxSim 晚期交互；
  - 都进行页面级检索。
- 修改位置：
  - 在检索表示训练阶段增加多层表示和多维前缀的训练约束；
  - 不改变“query 多向量对 page 多向量做 MaxSim”的基本接口。
- 是否改变 patch 数量：否。主要调整向量维度和提取层，不是按布局减少 patch 个数。
- 是否改变 MaxSim：否。仍采用相同 MaxSim，只是输入向量来自不同层和不同维度预算。
- 是否改变页面/区域检索粒度：否。主要仍是页面级视觉文档检索，不直接建模 BBox、OCR 区域或证据定位。

## 8. 与 ColParse 的区别

- ColParse 如何减少向量数量：
  - 使用文档解析模型识别布局区域；
  - 裁剪少量子图；
  - 每个子图重新编码为 local vector；
  - 再与整页 global vector 融合；
  - 从数百/数千 patch 向量缩减为少数布局区域向量。
- MM-Matryoshka 如何减少向量维度/层数：
  - 保留原有 patch 多向量数量；
  - 通过前缀维度训练减少每个向量的维度；
  - 从较浅层输出检索表示，并可利用 early exit 减少编码计算。
- 两者的离线编码成本差异：
  - ColParse：需要文档解析、区域裁剪、多个子图编码和整页编码；
  - MM-Matryoshka：不需要布局解析或区域重复编码，但完整预算仍保存大量 patch；选择浅层并 early exit 时可减少编码时间。
- 两者是否依赖布局解析：
  - ColParse：依赖外部布局解析；
  - MM-Matryoshka：不依赖布局解析。

## 9. 对本课题的启发

- 可借鉴的效率指标：
  - 每页向量数量；
  - 每向量维度；
  - 实际索引大小；
  - 页面编码时间；
  - query 编码时间；
  - MaxSim 时间；
  - GPU 显存；
  - 精度—成本曲线，而不是只报一个最好指标。
- 可借鉴的蒸馏思想：
  - 以完整 ColPali 表示为 teacher；
  - 让受限制的新表示保持原始页面排序分布；
  - 未来若训练 OCR/Layout 融合分支，可考虑让融合表示不偏离原始 ColPali 的页面检索行为。
- 是否适合作为后续扩展：适合。
  - 可作为毕业论文后续的效率扩展；
  - 前提是区域融合主模块已经有效；
  - 可研究融合 patch 表示在 `128/64/32` 维预算下的性能变化。
- 为什么不作为当前核心方法：
  - 它不解决 BBox、OCR 融合和区域级证据定位；
  - 训练多个二维预算会显著提高实现和实验复杂度；
  - 当前更需要先在 MMDocIR 上确定“页面级检索后的区域定位”是否是真实问题。

## 10. 当前结论

- 已理解：
  - MM-Matryoshka 是对 ColPali 类多向量检索进行二维预算训练的方法；
  - 二维分别是 Transformer 提取层和 embedding 前缀维度；
  - 它通过 Prefix 检索监督和层间分数蒸馏，让压缩表示仍可做 MaxSim；
  - 它主要解决精度、存储和编码计算之间的可调权衡。
- 尚不理解：
  - 各 backbone 最终选择哪些中间层，以及选择依据；
  - 训练 batch、负样本与具体超参数；
  - 代码是否已公开、具体 early-exit 实现是否真正支持所有 backbone；
  - 若与布局区域聚合同时使用，哪种压缩预算最合适。
- 需要以后验证：
  - 你的区域融合模型是否可以在较低维度下保持区域定位能力；
  - 减少向量维度和减少向量数量，哪一种更适合 MMDocIR；
  - 低维表示是否会更严重损害表格、数字、图片等细粒度区域检索。
- 不直接照搬的内容：
  - 完整二维 Matryoshka 联合训练；
  - 多个中间层检索头；
  - early-exit 训练；
  - 大规模多预算蒸馏。
