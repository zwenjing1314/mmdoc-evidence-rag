LayoutLMv3: Pre-training for Document AI with Unified Text and Image Masking

# 1. 主要解决问题

在这篇论文发布之前，文档理解领域（Document AI）的模型架构其实非常“割裂”。

简单来说，LayoutLMv3 要解决的核心问题是：**如何用一个统一的、无需复杂 CNN 骨干网络的架构，优雅地对齐文档中的文本（Text）、视觉（Vision）和布局（Layout）三种模态？**

在此之前的模型（如 LayoutLMv2）虽然也处理多模态，但存在两个明显的痛点，这也是 v3 致力于解决的：

### 1. 架构的“缝合感”与高昂的计算成本

早期的模型在处理文档图像时，通常严重依赖复杂的卷积神经网络（CNN，如 ResNet 或 Faster R-CNN）来提取视觉特征，然后再将这些视觉特征与文本的 Transformer 结合。

- **v3 的解决方式**：彻底抛弃了 CNN 骨干网络。它借鉴了 ViT（Vision Transformer）的思想，直接将文档图像切分成固定大小的**视觉 Patch**（这与 ColPali 的底层逻辑非常相似），将图像 Patch 和文本 Token 放在同一个 Transformer 中进行统一建模。

### 2. 模态之间缺乏细粒度的对齐机制

如何让模型知道“这个词的 Token”和“图像上的那个区域”是对应的？以前的模型往往只是粗暴地把特征拼在一起，或者依赖非常复杂的区域匹配预训练任务。

- **v3 的解决方式**：设计了三个巧妙的预训练目标，其中最关键的是 **WPA (Word-Patch Alignment)**。模型需要预测一个文本词是否被遮挡（Masked），并且要判断这个词对应的图像 Patch 是否也被遮挡。这种设计强制模型去学习文本和视觉 Patch 之间的空间对齐关系。

### 对你当前研究的启发

在思考面向多模态长文档的布局感知检索时，LayoutLMv3 里面有几个机制与你规划的方法架构高度契合，非常值得你在阅读时重点关注：

- **视觉 Patch 的处理**：LayoutLMv3 证明了纯基于 Patch 的视觉表示在文档任务中是完全可行的。这为你使用 ColPali 生成的 patch vectors 提供了有力的学术背书。
- **空间坐标编码（Spatial Embeddings）**：论文中详细描述了如何将 Bounding Box（左上角和右下角的坐标）转化为 2D 位置编码（2D Position Embedding）。你计划在“结构编码模块”中加入归一化坐标或 2D-RoPE，LayoutLMv3 的 2D 位置编码方式就是最经典的参考基线。
- **跨模态融合的思路**：论文探讨了文本 Token 和视觉 Patch 如何共享同一个注意力空间。当你在后期阶段（阶段四）考虑是否要进行联合优化或融合 OCR 文本时，这里的架构设计能提供直接的灵感。

# 2. 输入模态

LayoutLMv3 的输入包含 **三种模态（Modalities）**。这三者在经过 Embedding（嵌入）处理后，会被拉平并拼接成一个统一的长序列，直接送入一个多模态 Transformer 中进行计算。

### 三种核心输入模态

**1. 文本模态 (Text)**

- **来源**：通过 OCR 引擎提取（或直接从数字文档解析）出的文本序列。
- **表示方式**：经过 Tokenizer 分词后，转化为 Token 序列。这部分包含基础的词向量（Word Embedding）和表示阅读顺序的一维位置编码（1D Position Embedding）。

**2. 视觉模态 (Vision / Image)**

- **来源**：原始的文档整图。
- **表示方式**：这是 LayoutLMv3 区别于前代的最关键创新。它彻底抛弃了 CNN（如 Faster R-CNN），直接借鉴了 ViT 的做法，将图片切分成固定大小的网格（例如 16×16 的 Patch）。然后将这些 Patch 展平，通过线性投影（Linear Projection）映射为视觉 Token。
- **联系你的研究**：这种纯基于 Patch 的视觉处理方式，与你计划使用的 **ColPali 基座**在底层逻辑上是完全一致的。

**3. 布局模态 (Layout / Spatial)**

- **来源**：文本 Token 在原图中的边界框（Bounding Box, BBox）。
- **表示方式**：提取 BBox 的左上角和右下角坐标 `(x0, y0, x1, y1)`。将原图长宽离散化（通常归一化到 0-1000 的区间），然后在 X 轴和 Y 轴的嵌入表里查找对应坐标的向量。将这些向量拼接后，形成 **2D 位置编码 (2D Position Embedding)**。

> **模态是如何融合的？** 布局模态（2D 坐标）实际上是作为一种“空间属性”，直接与文本模态（词向量、1D 位置编码）**相加**，形成最终的文本特征。最后，融合了布局的文本 Token 序列与图像 Patch Token 序列拼接，共同输入给 Transformer。

# 3. 布局信息加入

在 LayoutLMv3 中，布局信息（Layout/BBox）是在**模型的最前端——嵌入层（Embedding Layer）\**加入的，并且它\**仅仅绑定在文本模态（Text Tokens）上**。

具体来说，它在数据进入 Transformer 编码器主体进行注意力计算**之前**，就通过“向量相加（Element-wise Addition）”的方式与文本特征融为一体了。

我们可以把这个过程拆解为以下三个步骤：

### 1. 坐标的离散化 (Discretization)

OCR 识别出一个词后，会给出这个词在文档图片上的物理边界框坐标：左上角 `(x0, y0)` 和右下角 `(x1, y1)`。 由于图片的真实像素尺寸大小不一，LayoutLMv3 首先会将这些坐标统一**归一化并离散化**到一个固定的整数区间（通常是 0 到 1000）。

### 2. 独立坐标的向量映射 (Embedding Lookup)

模型内部维护了两个可学习的“空间坐标词表”（X 轴词表和 Y 轴词表）。 它会将离散化后的坐标分别投入这些词表中查表，同时也会计算框的宽度 `w` 和高度 `h`：

- 在 X 轴词表中查 `x0`, `x1`, `w`
- 在 Y 轴词表中查 `y0`, `y1`, `h` 将这些查到的向量拼接或组合起来，就形成了一个专门代表这个词位置的 **2D 空间位置编码（2D Spatial Position Embedding）**。

### 3. 与文本特征相加 (Element-wise Addition)

这是最关键的一步。对于输入序列中的某一个词，它最终送入 Transformer 的向量表示是由以下几部分**直接相加**构成的：

```
最终 Token 向量 = 
  词汇本身的意思 (Word Embedding) 
  + 在句子中的阅读顺序 (1D Position Embedding) 
  + 在页面上的二维空间位置 (2D Spatial Position Embedding) 
  + 属于哪个段落/文档块的标识 (Segment Embedding)
```

# 4.  输出类型

LayoutLMv3 本身是一个 **预训练基座模型（Encoder-only）**，类似于 BERT 或 RoBERTa。它的直接输出是**融合了文本、布局和视觉信息的隐状态向量表示（Hidden States）**。

通过在这些输出向量顶部添加不同的任务头（Task Heads）并进行微调（Fine-tuning），论文在实验部分展示了它在**分类、抽取和问答**这三大类任务上的卓越表现，但它**并没有专门针对“检索（Retrieval）”任务进行设计和评估**。

具体来说，它的下游任务表现如下：

### 1. 分类 (Classification)

- **任务类型**：文档图像分类（Document Image Classification）。
- **具体做法**：模型取序列起始位置的 `[CLS]` 标记的输出向量，接一个简单的线性分类器，判断这篇文档属于什么类别（如：发票、简历、备忘录等）。
- **论文使用的数据集**：RVL-CDIP。

### 2. 抽取 (Extraction)

这是 LayoutLM 系列最核心也最擅长的任务，通常被称为“语义实体识别”（Semantic Entity Recognition, SER）或关系抽取（Relation Extraction, RE）。

- **任务类型**：表单理解、票据信息抽取。
- **具体做法**：对输出的每一个文本 Token 向量进行分类（序列标注，类似于 BIO 标签），判断这个词是属于“买方名称”、“总金额”还是“日期”。
- **论文使用的数据集**：FUNSD（表单）、CORD（收据）。

### 3. 问答 (Question Answering)

- **任务类型**：文档视觉问答（Document Visual Question Answering, DocVQA）。
- **具体做法**：通常建模为“抽取式问答（Extractive QA）”。模型将用户的问题（Query）和文档内容拼接在一起输入，然后在输出的 Token 序列中预测答案的“起始位置（Start）”和“结束位置（End）”。

### 为什么没有“检索（Retrieval）”？（对你论文的启示）

LayoutLMv3 默认采用的是一种深度融合的架构：**文本、布局和图像从一开始就拼在一起，通过多层 Transformer 产生了极其复杂的自注意力交互（Self-Attention）**。

如果你想用 LayoutLMv3 做检索，通常只能采用 **Cross-Encoder（交叉编码器）** 的模式：将“查询（Query）”和“文档（Document）”拼接后一起输入模型打分。

- **致命缺点**：速度极慢。面对百万级别的文档库，你无法预先计算文档的向量，每次用户提问都必须把 Query 和所有的 Document 拼起来过一遍庞大的 Transformer 模型，这在真实场景的检索召回阶段是不可接受的。

> **你选用的 ColPali 的优势与两者的互补：**
>
> 这正是你基于 **ColPali** 做检索研究的价值所在。ColPali 是一种 **Dual-Encoder（双塔） + Late Interaction（晚期交互 / MaxSim）** 架构。它可以离线把所有文档页面独立编码成 Patch 向量存入数据库，检索时只需计算 Query 向量和预计算的 Patch 向量的相似度，速度极快。
>
> 你的研究本质上是在**吸收 LayoutLM 系列“细粒度布局感知”的优点，同时保持 ColPali“多向量高效检索”的优势**。这也是为什么你在第一版架构中选择在打分阶段做“页面级 MaxSim + 区域级 MaxSim”，而不是像 LayoutLM 那样把 Query 和 Document 塞进同一个模型里。

注意：LayoutLMv3 主要面向文档理解，不是 ColPali 这种页面检索模型。

# 5. 文本输入

在 LayoutLMv3 中，OCR 提取出的文本并不是直接送入模型的，而是要经过一个精细的多重嵌入（Multi-Embedding）和融合过程。

文本模态的最终输入向量（Token Representation）是由四个部分逐元素相加（Element-wise Addition）构成的。以下是具体的编码步骤和数学表达：

### 1. 分词与边界框对齐 (Tokenization & BBox Alignment)

首先，OCR 引擎会输出一组**词（Words）\**以及对应的\**边界框（Bounding Boxes）**。 LayoutLMv3 使用的是 RoBERTa 的 **BPE（Byte-Pair Encoding）** 分词器。这会带来一个工程细节：一个完整的 OCR 词可能会被切分成多个子词（Subwords）。

- **对齐策略**：如果一个词被切分成多个子词，这些子词将**共享同一个原始词的边界框坐标**。

### 2. 四重嵌入特征的提取

对于序列中的第 i 个子词 token，模型会提取以下四种特征：

- **词嵌入 (Word/Token Embedding, Eword)**： 将分词后的 token 映射为高维语义向量。这包含了词汇本身的纯文本语义。

- **一维位置编码 (1D Position Embedding, E1D)**： 表示该 token 在整个阅读序列（Reading Order）中的绝对索引位置（如：第 5 个词、第 6 个词）。这使得模型能够理解文本的线性逻辑顺序。

- **二维空间编码 (2D Spatial Embedding, E2D)**： 获取该 token 对应的归一化坐标 x0,y0,x1,y1 以及宽 w 和高 h。模型分别在 X 轴和 Y 轴的嵌入表（Embedding Table）中查表，将其相加或拼接。

  E2D=EX(x0)+EX(x1)+EX(w)+EY(y0)+EY(y1)+EY(h)

- **片段编码 (Segment / Token Type Embedding, Eseg)**： 用于区分不同的模态或片段（例如，在问答任务中区分 Question 和 Document 段落）。

### 3. 特征融合相加

最终，第 i 个文本 token 的输入表示 hi 是上述四个向量的直接加和，外加一个层归一化（Layer Normalization）：

hi=LayerNorm(Eword(i)+E1D(i)+E2D(i)+Eseg(i))

这个融合后的向量 hi 既包含了“这个词是什么意思”，又包含了“它在句子里的什么位置”，还包含了“它在页面物理排版中的确切坐标”。这些处理好的文本 token 会和视觉 Patch token 在同一层被拉平拼接，送入 Transformer。

> **工程避坑提示** 在实际复现或处理类似多模态数据（如你的 MMDocIR 数据集）时，**“文本序列长度 (Sequence Length)” 和 “视觉 Patch 数量”的拼接上限**通常是显存爆炸的重灾区。LayoutLMv3 的文本长度通常截断在 512，如果一份长文档 OCR 结果过长，就必须进行滑窗切割（Sliding Window），这会导致跨页或长跨度布局上下文的丢失。

# 6. 图像输入

在 LayoutLMv3 中，图像页面的处理方式彻底抛弃了前两代使用的 CNN（卷积神经网络），而是直接采用了 **ViT (Vision Transformer)** 的标准做法——**线性 Patch 投影（Linear Patch Projection）**。

具体到图像是如何切分、数量和维度的，我们可以用数学和工程的视角拆解如下：

### 1. 图像的缩放与切分 (Patchification)

无论原始输入的文档图片是 A4 纸比例还是收据的细长比例，LayoutLMv3 首先都会将原始图像强行缩放（Resize）到一个固定的标准分辨率，通常是 224×224 像素。

随后，模型将这张 224×224 的图像切割成互不重叠的、大小固定的正方形网格（Grid）。论文中设定的 Patch 尺寸（Patch Size, P）为 16×16 像素。

### 2. Patch 的数量 (Number of Patches)

有了总分辨率和单个 Patch 的大小，Patch 的数量可以通过简单的除法得出：

- **网格划分**：宽和高方向各有 224/16=14 个 Patch。
- **总 Patch 数量**：14×14=196 个 Patch。

所以，一张文档图片在 LayoutLMv3 的视觉流中，会被精确地切分成 **196 个视觉 Patch**。

### 3. Patch 的维度映射 (Dimensionality)

切分完成后，这 196 个图像块需要转换成 Transformer 能理解的向量形式：

- **展平前的原始维度**：每个 Patch 是一个包含 RGB 三通道的小图片，维度为 3×16×16。
- **拉平（Flatten）**：将其展开成一个一维向量，长度为 3×16×16=768。
- **线性投影（Linear Projection）**：这 196 个长度为 768 的向量，会通过一个线性层（可以理解为一个权重矩阵），映射到与文本 Token 相同的隐藏层维度（Hidden Size, D）。
  - 在 **LayoutLMv3-Base** 模型中，D=768。
  - 在 **LayoutLMv3-Large** 模型中，D=1024。

最后，模型还会给这 196 个视觉向量加上一个**可学习的一维位置编码（1D Learnable Position Embedding）**，让模型知道这个 Patch 原本是在图片的左上角还是右下角。这批向量随后就可以直接跟前面处理好的文本 Token 序列拼接在一起了。

**结合你的论文研究来看：这是一个重要的效率与精度的折中点**

LayoutLMv3 把图片强行压到 224×224，只产生 196 个 Patch。这在计算上非常**高效**，但代价是**视觉分辨率极低**。对于密集排版的长文档或极小的表格数字，196 个 Patch 往往会把相邻的几行字糊成一团，导致纯视觉特征丢失大量细节。

你在论文第一版计划使用的 **ColPali**，其底层的视觉编码器（如基于 PaliGemma / SigLIP）通常会接受高得多的输入分辨率（例如 1024×1024 或动态高分辨率）。

- 如果按照 1024×1024 分辨率和 14×14 的 Patch 大小来算，一张图会产生高达 **5329 个 Patch**！
- 这正是你论文中**“H4：区域聚合带来的向量数量、存储和延迟变化”** 这个研究问题（Research Question）的核心背景。因为一页保存几千个 Patch，检索成本极高，你的区域聚合（Region Aggregation）模块就是为了解决这个“多向量开销”而存在的。

# 7. 布局输入

在 LayoutLMv3 中，布局信息（Bounding Box, 简称 BBox）的归一化和二维位置编码（2D Position Embedding）的设计非常经典。它的核心思想是将连续的物理像素坐标转化为离散的、可学习的 Embedding 向量。

以下是具体的数学和工程实现细节：

### 1. BBox 坐标是如何归一化的？

OCR 引擎提取出的原始坐标是基于原始图片像素尺寸的。为了让模型能够处理任意长宽比和尺寸的图片，LayoutLMv3 采用了以下两步归一化：

- **相对原图比例映射**：首先，取出 BBox 的左上角和右下角坐标 `(x0, y0, x1, y1)`，将 x 轴坐标除以图片的真实宽度 W，将 y 轴坐标除以图片的真实高度 H。
- **离散化到 0-1000 整数区间**：将上一步得到的相对比例（0 到 1 之间的小数）乘以 1000，并取整。 这样一来，所有的坐标信息都被统一拉伸/压缩到了一个 `[0, 1000]` 的标准离散网格上。坐标变成了类似于词汇表索引（ID）一样的整数（例如：x0=125, y1=850），这为后续的“查表”操作做好了准备。

### 2. 采用了什么样的二维位置编码（2D Position Embedding）？

当坐标变成了 0-1000 的整数后，LayoutLMv3 并没有直接把这 4 个数字丢给模型，而是做了一套精细的**空间特征解耦与映射**：

- **引入宽 (width) 和高 (height)**：除了基础的 `x0, y0, x1, y1`，模型还会显式计算 BBox 的宽度 w=x1−x0 和高度 h=y1−y0。这样一共就有了 **6 个空间特征向量**。
- **建立独立的 Embedding Tables（嵌入表）**： 模型内部初始化了用于 X 轴和 Y 轴特征的可学习的 Embedding 层。
  - X 轴相关的特征（x0,x1,w）在 X 轴的 Embedding 表中进行查表映射。
  - Y 轴相关的特征（y0,y1,h）在 Y 轴的 Embedding 表中进行查表映射。
- **向量融合**：这 6 个经过查表得到的高维向量会被结合起来（通常是通过拼接并线性投影，或者直接加和），形成一个统一的向量。这个向量就是专属于当前文本的 **2D 布局位置编码（2D Layout Position Embedding）**。

### 3. LayoutLMv3 相较于 v1/v2 的一个关键创新：Segment-level

在你阅读 LayoutLMv3 时，需要特别注意它与前两代的一个重要区别，这与你的“区域聚合”思路不谋而合：

- **LayoutLMv1 和 v2：** 采用的是词级别（Word-level）布局位置。也就是一句话里如果有 10 个词，每个词都要有一个自己极其紧凑的小 BBox。
- **LayoutLMv3：** 改为采用片段级别（Segment-level）布局位置。论文认为，属于同一个文本片段（比如同一行、同一个段落）的词汇通常在表达相同的语义。因此，v3 让同一个片段里的所有词语 token **共享**这整个片段的大的 2D BBox 编码。

> **对你研究的启示：** LayoutLMv3 证明了**粗粒度的“段落/区域级（Segment-level）”布局信息完全能支撑起优异的模型性能**，甚至比细粒度的“词级别”更好，因为它减少了对 OCR 词级对齐的严苛依赖。 这直接为你设计的 **Patch-to-Region（把 Patch 聚合到大区域 BBox 上）** 提供了极佳的理论支撑——你不需要强求每一个 patch 必须精确对应一个单词，对应到一个具有明确语义的“布局区域”可能反而是更优解。

# 8. 模态融合

在 LayoutLMv3 中，文本 Token 和图像 Patch 的拼接与交互方式可以总结为：**简单粗暴的序列拼接（Sequence Concatenation）**，加上**极度深度的自注意力交互（Deep Self-Attention）**。

这种模态融合方式被称为“早期融合（Early Fusion）”或“单流架构（Single-stream Architecture）”。以下是它在网络内部流转的数学与逻辑拆解：

### 1. 序列的直接拼接 (Concatenation)

在进入 Transformer 编码器主体之前，文本和图像各自已经完成了初始的 Embedding 处理：

- **文本序列**：提取了词汇、1D 顺序和 2D 布局特征后，形成一个长度为 L 的矩阵 T∈RL×D（其中 D 是隐藏层维度，如 768）。
- **图像序列**：经过 16x16 切分和线性投影后，加上图像的一维位置编码，形成一个长度为 M 的矩阵 I∈RM×D（在 LayoutLMv3 中 M 固定为 196）。

此时，模型只是在序列长度（Sequence Length）的维度上，将这两个矩阵直接拼接在一起，形成一个融合的输入大矩阵 X：

X=[T;I]∈R(L+M)×D

如果文本长度限制在 512，那么这个拼接后的总序列长度就是 512+196=708。

### 2. 交互核心：全局多头自注意力 (Global Multi-Head Self-Attention)

拼接后的矩阵 X 会被送入多层 Transformer Encoder（例如 12 层或 24 层）。在这里，模态之间的“壁垒”被彻底打破，文本 Token 和图像 Patch 共享同一个注意力空间。

在每一层的自注意力计算中，模型会通过线性变换生成查询矩阵 Q、键矩阵 K 和值矩阵 V。注意力权重的计算公式为标准形式

由于输入包含了两种模态，这个注意力矩阵（Attention Matrix）实际上隐式地包含了四种交互关系：

1. **Text-to-Text (T-T)**：文本理解上下文语义。
2. **Image-to-Image (I-I)**：视觉 Patch 理解全局图像结构。
3. **Text-to-Image (T-I)**：**跨模态！** 比如文本中的“Total Amount”这个词，它的 Q 会去计算图像中右下角数字所在 Patch 的 K 的注意力权重。
4. **Image-to-Text (I-T)**：**跨模态！** 视觉 Patch 也会根据图像特征去寻找对应的文本 Token 以获取语义补充。

经过多层堆叠后，输出的每一个向量（无论它最初是文本还是图像），都已经深深“吸收”了另一模态的信息。

# 9. Transformer

在 LayoutLMv3 中，Transformer 采用的是典型的**单流架构（Single-stream Architecture）**。

在多模态大模型的发展史中，单流和双流是最核心的架构分歧之一。LayoutLMv3 选择单流架构，意味着文本和图像在非常早期的阶段（输入层）就被强行拼接在了一起，并进入同一个 Transformer 编码器中进行处理。

以下是关于单流架构下参数共享机制的详细拆解：

### 1. 共享的参数（核心 Transformer 层完全共享）

一旦拼接好的序列进入 Transformer 编码器主体（Encoder Blocks），**所有的网络参数对于文本 Token 和图像 Patch 来说是 100% 共享的**。具体包括：

- **注意力投影矩阵 (WQ,WK,WV)**： 这是最关键的共享参数。无论是计算文本的 Query，还是图像的 Query，模型使用的是同一个 WQ 矩阵。这种参数共享强制模型在同一个高维表示空间内去理解“文本语义”和“视觉特征”，从而实现前面提到的深度跨模态注意力交互（Text-to-Image, Image-to-Text）。
- **前馈神经网络 (FFN) 的权重**： Transformer 每一层注意力之后的两层 MLP（全连接层）对于所有模态的 token 也是完全共享的。
- **层归一化 (Layer Normalization)**： 模型中所有的 LayerNorm 参数（缩放和平移因子）都一视同仁地应用于融合后的长序列。

### 2. 独立的参数（输入前期的 Embedding 层严格隔离）

尽管 Transformer 主体共享参数，但在进入 Transformer **之前**的特征提取阶段，各模态的参数是完全独立、互不干扰的：

- **文本专属参数**：
  - 词嵌入矩阵（Word Embedding Table）。
  - 1D 相对/绝对阅读顺序位置编码。
  - 2D 空间坐标（X 轴和 Y 轴）的 Embedding 词表。
- **图像专属参数**：
  - 用于将 16×16×3 的 RGB 像素块映射到高维（如 768 维）的**线性投影矩阵（Linear Projection Weights）**。
  - 图像专属的 1D 位置编码（Image Position Embedding），用于标识 Patch 在原始 14×14 网格中的位置。
- **模态类型标识（Segment/Modality Embedding）**： 虽然模型在深层共享了所有计算参数，但它会通过一个独立的“类型参数”告诉网络：“这个 token 是文本，那个 token 是视觉 Patch”。

### 对底层架构设计的深层启示

了解 LayoutLMv3 的单流和参数共享机制后，我们可以更清晰地看到不同架构在“检索 vs 理解”任务上的鸿沟。

**单流架构（如 LayoutLMv3）**： 由于 WQ,WK,WV 是共享的，且序列在一开始就拼在一起，它的每一次前向传播（Forward Pass）都在计算极度复杂的跨模态 Attention。这让它在做文档信息抽取（Token 级分类）时拥有无与伦比的精度，因为图文特征融合得非常彻底。但这种架构无法将 Query（查询）和 Document（文档）解耦缓存，导致搜索延迟呈指数级增长。

**双流/晚期交互架构（如基于 SigLIP/PaliGemma 的架构设计）**： 这也是为什么你的毕业论文路线能够成立的核心原因。如果采用纯视觉基座来离线编码页面 Patch，将文档的视觉特征与用户的文本查询分离开来（保持双塔独立编码），把最终的相似度计算推迟到最后一步（MaxSim）。这就巧妙地避开了单流架构中昂贵的联合计算成本，使得在长文档或多页场景下的海量区域检索成为可能。

# 10. 输出表示

在 LayoutLMv3 经过多层 Transformer 的深度交互后，输出的是一个**统一的、融合了多模态特征的隐藏状态序列（Hidden States Sequence）**。

在 PyTorch 的代码实现中，这通常对应着模型最后一层的输出张量，形状为 `(Batch_Size, Sequence_Length, Hidden_Dim)`。

要从中获取特定的 Token、Patch 或整页表示，核心操作是**按索引切片（Sequence Slicing）**。因为在输入时，文本和图像是按固定顺序拼接的。典型的拼接顺序为： `[CLS] + Text Tokens + [SEP] + Image Patches`

以下是获取这三种表示的具体方法及其下游用途：

### 1. 整页表示 (Page-level Representation)

- **获取方式**：直接提取输出序列的**第 0 个位置**，即 `[CLS]`（在基于 RoBERTa 的分词器中通常是 `<s>`）的输出向量。
  - 代码逻辑类似：`page_rep = last_hidden_state[:, 0, :]`
- **包含的信息**：由于自注意力机制，这个 `[CLS]` 向量在逐层传递中“看”到了整页的 OCR 文本、所有的布局坐标以及所有的视觉 Patch。因此，它被视为整张页面的全局高维浓缩表示。
- **经典用途**：**文档图像分类**（如 RVL-CDIP 数据集）。在这个向量之上接一个简单的线性分类器（Linear Layer），即可判断该页是发票、简历还是科研论文。

### 2. 文本 Token 表示 (Token Representation)

- **获取方式**：提取 `[CLS]` 之后、`[SEP]` 之前的序列片段。假设文本长度为 L。
  - 代码逻辑类似：`token_reps = last_hidden_state[:, 1 : L+1, :]`
- **包含的信息**：这些向量不仅包含词汇本身的语义，还融合了它在页面上的物理 BBox 上下文，以及对应区域的视觉特征（通过软对齐学到）。
- **经典用途**：**序列标注与信息抽取**（如 FUNSD 表单抽取）。对这 L 个向量逐一进行分类，判断哪个 token 是“键（Key）”、哪个 token 是“值（Value）”。

### 3. 图像 Patch 表示 (Patch Representation)

- **获取方式**：提取序列的最后一部分。由于 LayoutLMv3 将图片切分为 14×14=196 个 Patch，提取最后 196 个位置的向量即可。
  - 代码逻辑类似：`patch_reps = last_hidden_state[:, -196:, :]`
- **包含的信息**：融合了全局图像结构和相关文本语义的视觉区域特征。
- **经典用途**：在预训练阶段用于 **MIM（掩码图像建模）**，即预测被遮挡 Patch 的原始视觉 Token。在微调阶段，这部分特征很少单独拿出来做任务，而是作为文本 token 和 `[CLS]` 判断的辅助信息。

### 💡 与你的论文研究（ColPali 架构）的深度映射

弄清 LayoutLMv3 的输出切片逻辑，对你设计 **MMDocIR 上的 Patch-to-Region 对齐实验**非常有帮助。你的研究与 LayoutLMv3 在输出处理上有几个决定性的差异：

1. **没有文本 Token 序列**： ColPali 是纯视觉的，它的输出仅仅是一个由大量 Patch 表示组成的矩阵（例如 1024 分辨率下的数千个 Patch）。没有 `[CLS]`，也没有文本 Token。
2. **整页表示的获取差异（MaxSim）**： LayoutLMv3 用 `[CLS]` 代表整页；而 ColPali 是保留所有的 Patch 向量。在计算页面相关性时，ColPali 使用 **Late Interaction (MaxSim)**——让 Query 的每个 Token 去与页面内所有的 Patch 算相似度，取最大值后再求和，以此代表“页面得分”。
3. **如何获得 Region（区域）表示**： 这正是你论文的核心贡献点（阶段二的模块）。既然 ColPali 输出的是纯 Patch 矩阵，你无法像 LayoutLMv3 那样直接取出“Token 表示”来代表一个区域。你必须拿到外部提供的 BBox 坐标，将其映射到这数千个 Patch 组成的网格坐标系中，然后通过 **RoI Align、IoU 加权或简单的均值池化（Mean Pooling）**，把框内的 Patch 向量“压缩”成一个或几个 Region 向量。

# 预训练任务与损失函数

## 1. 输入被遮挡了什么

LayoutLMv3 的核心创新就在于它的预训练任务设计。论文副标题是 *“Pre-training for Document AI with Unified Text and Image Masking”*（基于统一文本与图像掩码的文档 AI 预训练），这三个预训练任务直接决定了模型如何学习跨模态的深层关联。

在 LayoutLMv3 中，总共有 **三个** 预训练任务。以下是每一个任务中“什么被遮挡了”、“保留了什么”以及对应损失函数的详细拆解：

### 1. MLM (Masked Language Modeling) - 掩码语言建模

这个任务逼迫模型结合“视觉”和“布局”来猜词。

- **什么被遮挡了**： 输入序列中 **30% 的文本 Token** 被遮挡。其中 80% 替换为 `[MASK]`，10% 替换为随机词，10% 保持不变（标准的 BERT 策略）。
- **什么被绝对保留了（核心细节！）**： **被遮挡词的二维空间坐标（2D BBox）被完全保留。** 也就是说，模型知道这里“空了一个词”，并且明确知道这个词在页面上的具体物理位置。
- **模型要做什么**： 利用未被遮挡的上下文文本，加上原图上那个物理位置对应的视觉 Patch，预测出原本的词。
- **损失函数**： 标准的**交叉熵损失 (Cross-Entropy Loss)**，仅在被遮挡的 Token 上计算预测词汇概率分布与真实词汇的差异。

### 2. MIM (Masked Image Modeling) - 掩码图像建模

借鉴了 BEiT 等纯视觉模型的做法，逼迫模型通过文本和周围图像来脑补缺失的画面。

- **什么被遮挡了**： **约 40% 的图像 Patch** 被遮挡。特别注意的是，它采用的是**块状掩码 (Blockwise Masking)**而不是随机散点掩码。也就是说，它会直接在图上挖掉一整块（比如挖掉整个表格的一角），这比随机遮盖单个 16×16 的 Patch 难度大得多。这些被遮盖的特征被替换为一个可学习的 `[MASK]` 向量。
- **什么被保留了**： 剩余 60% 的图像 Patch 特征，以及所有的文本和布局信息。
- **模型要做什么**： 论文没有让模型去重建原始的 RGB 像素（因为太难且充满噪声），而是用一个预训练好的离散视觉分词器（Discrete VAE，比如 DALL-E 的图像 tokenizer），把整张图变成离散的“视觉词汇 IDs”。模型需要预测被遮挡区域对应的 **离散视觉 Token ID**。
- **损失函数**： 同样是**交叉熵损失 (Cross-Entropy Loss)**，分类目标是预训练离散视觉词表的大小（通常是 8192 个类）。

### 3. WPA (Word-Patch Alignment) - 词与图像块对齐

前两个任务是各自模态内部的掩码重建，而 WPA 是专门为了强制产生**跨模态对齐**而设计的任务。

- **什么被遮挡了**： 这个任务**不产生新的遮挡**，它直接复用 MLM 和 MIM 产生的掩码状态。
- **模型要做什么**： 针对所有**未被遮挡的文本 Token**，模型需要进行二分类判断：**“这个词对应的物理位置上的图像 Patch，在 MIM 任务中是否被遮挡了？”**
- **损失函数**： **二元交叉熵损失 (Binary Cross-Entropy Loss, BCE) 或者 2 分类交叉熵损失**。

### 总体损失函数 (Total Loss)

在预训练阶段，总损失函数就是这三者的简单相加：

L=LMLM+LMIM+LWPA

### 💡 对你毕业论文设计的深层启示

在你的论文规划“阶段四：训练扩展”中，你提到了如果具备独立训练数据，要加入“区域级对比/排序损失”。LayoutLMv3 的预训练任务提供了一个非常不同的视角：

1. **生成式 vs 对比式**：LayoutLMv3 的 MLM 和 MIM 都是**生成式重建（Reconstruction）**，为了让模型“学得更杂、理解更深”。而你使用的是 ColPali，它天然是为了对比学习（Contrastive Learning）而生的。
2. **无需重新发明轮子**：如果你在阶段四对 ColPali 增加区域感知能力，**千万不要去模仿 MLM 或 MIM 去做掩码重建**，那需要极大的算力和数据。
3. **借鉴 WPA 的思想**：WPA 这种**显式对齐判别**非常值得借鉴。你可以设计一个轻量级的对比损失（Contrastive Loss），正样本是“查询文本 + 它真实对应的 Region 视觉向量”，负样本是“查询文本 + 同一页的其他 Region 视觉向量”，以此来微调你引入的“区域聚合模块”。

## 2. 预测目标是什么

在 LayoutLMv3 的三个预训练任务中，预测目标（Prediction Targets）设计得非常巧妙。为了保证训练的稳定性和效率，这三个任务都没有去预测连续的实数值（例如直接预测坐标偏移量或还原真实的 RGB 像素），而是全部转化为了**离散的分类问题**。

具体到每一个任务，其网络最后一层的“预测目标”如下：

### 1. MLM (Masked Language Modeling) 的预测目标

- **预测目标是什么**：被遮挡位置的**原始文本词汇 ID (Text Token ID)**。
- **具体细节**：模型的输出层（通常是一个维度为 `Vocab_Size` 的全连接层，比如 RoBERTa 词表大小为 50,265）会输出一个概率分布。预测目标就是让被遮挡位置输出的概率分布，尽可能逼近分词器（Tokenizer）最初给这个词分配的真实整数 ID。
- **本质**：一个包含数万个类别的**多分类问题**。

### 2. MIM (Masked Image Modeling) 的预测目标

- **预测目标是什么**：被遮挡图像块对应的**离散视觉 Token ID (Discrete Visual Token ID)**。
- **具体细节（核心难点）**：模型**绝对不是**去预测被遮挡的 16×16 像素块里的原始 RGB 色彩（因为预测像素包含太多高频噪声，且对文档理解毫无帮助）。 LayoutLMv3 借用了一个预训练好的离散视觉分词器（Discrete VAE，类似于 DALL-E 中使用的图像 Tokenizer），提前把整张原始图片“翻译”成了一串离散的数字 ID（通常视觉词表大小约为 8192）。在 MIM 任务中，模型的目标就是猜出那个被盖住的 Patch，它对应的“视觉词汇 ID”是这 8192 个数字中的哪一个。
- **本质**：一个包含 8192 个类别的**多分类问题**。

### 3. WPA (Word-Patch Alignment) 的预测目标

- **预测目标是什么**：一个**二元分类标签（Binary Label: Aligned 或 Unaligned）**。
- **具体细节**：对于输入序列中每一个**没有被遮挡**的文本 Token，网络构建一个简单的二分类头。
  - 如果该文本所在的物理区域对应的图像 Patch 在 MIM 任务中**没有**被遮挡，真实标签就是 `Aligned (1)`。
  - 如果对应的图像 Patch 在 MIM 任务中**被遮挡**了，真实标签就是 `Unaligned (0)`。
- **本质**：一个简单的 **0/1 二分类问题**。

### 💡 对你设计“区域聚合模块”微调的启示

注意看 LayoutLMv3 的设计哲学：**它把所有复杂的跨模态重建，都降维成了“选 ID”或者“判别是与否”的分类问题。**

回到你的毕业论文：如果你在**阶段四**想要微调你的 ColPali 区域聚合模块，你也可以采用类似降维打击的思路。不要让模型去“生成”完美的区域向量，而是让模型做**排序（Ranking）或对比分类（Contrastive Classification）**。

例如，你可以把预测目标设计为：给定一个 Query，在当前页面的 20 个切分好的 BBox Region 中，**预测哪一个 Region ID 是真正的证据区域**（这本质上变成了一个有 20 个类别的选择题）。这种预测目标比计算复杂的重构损失要容易收敛得多，也完全契合你“定位证据”的研究初衷。

## 3. 正负样本如何构造

在探讨 LayoutLMv3 的正负样本构造之前，需要先理清一个非常重要的学术概念差异：

**LayoutLMv3 的预训练本质上是“生成式/掩码预测（Masked Prediction）”，而不是“对比学习（Contrastive Learning）”。**

因此，在 MLM（掩码语言）和 MIM（掩码图像）任务中，并不存在严格意义上的“正样本”和“负样本”对。它们是标准的多分类问题——真实的 Token ID 就是唯一的目标标签，词表里的其他所有 ID 都在 Softmax 中自然成为了“背景板”。

真正涉及到类似“正负样本”概念的，只有那个用于判断跨模态对齐的二分类任务：**WPA (Word-Patch Alignment)**。

在 WPA 任务中，正负样本（即标签 1 和 0）的构造完全依赖于 MIM 任务中对图像 Patch 的“人工随机遮挡”。具体构造逻辑如下：

### WPA 任务的正负样本构造

WPA 任务**只针对那些没有被遮挡的文本 Token** 进行计算。对于每一个可见的文本 Token，模型要判断它的视觉对齐状态：

- **正样本 (Aligned，标签设为 1)**：
  - **条件**：该文本 Token 对应的物理 BBox 所覆盖的图像 Patch，在 MIM 任务中**没有被遮挡（Unmasked）**。
  - **物理意义**：模型既能看到这个词的文本语义，又能看到它对应区域的真实视觉像素特征。这就是一个天然对齐的“正样本”。
- **负样本 (Unaligned，标签设为 0)**：
  - **条件**：该文本 Token 对应的物理 BBox 所覆盖的图像 Patch，在 MIM 任务中**被遮挡了（Masked，替换为了 `[MASK]` 向量）**。
  - **物理意义**：模型看到了这个词的文本语义，但当它的注意力机制根据 BBox 坐标去图像侧寻找视觉特征时，发现那里是一团“黑影”（掩码向量）。由于视觉信息缺失，这被定义为不对齐的“负样本”。

> **一个小细节**：如果一个文本 Token 本身在 MLM 任务中就被遮挡了，那么它会直接被排除在 WPA 的计算之外，既不做正样本也不做负样本，以避免任务过于复杂导致的梯度混乱。

### 这对你构思 ColPali 对比损失的启示（核心差异点）

弄懂了 LayoutLMv3 的构造方式，你会发现它与你打算在阶段四做的“区域级对比/排序”有着本质的区别，这也是你论文设计的创新空间所在：

**1. 负样本的来源完全不同：**

- **LayoutLMv3**：负样本是“人工制造的视觉缺失”（把对应的 Patch 盖住）。模型学到的是“有”和“无”的区别。
- **你的区域检索设计**：如果要做对比学习（InfoNCE 损失），你的负样本不能是“瞎盖住的区域”，而必须是“同一页上其他真实存在的错误区域（In-batch/In-page Negatives）”。模型需要学会在多个真实区域中，挑出和 Query 语义最匹配的那一个。

**2. 任务难度的进阶（Hard Negatives）：**

- LayoutLMv3 的 WPA 任务相对简单，因为它只需要判断“我的眼睛有没有被蒙上”。
- 在检索任务中，如果一页里有三个表格，Query 是问“表格A的利润”，那么表格 B 和表格 C 的区域表示就是极其优质的**困难负样本（Hard Negatives）**。这种基于真实版面结构的困难负样本构造，是 LayoutLMv3 这种掩码任务无法做到的，但却是提升检索定位精度的关键。

通过对比，你可以很清晰地在论文中论证：为什么在面向检索的场景下，摒弃 LayoutLMv3 的掩码预测，转向基于页面内候选区域的对比学习（Contrastive Learning），是一个架构上更优的选择。

## 4. 损失如何计算

LayoutLMv3 的预训练由三个任务共同构成。为了让你一目了然，我将这三个任务在“遮挡内容”、“损失计算方式”**以及**“监督目标”上的核心机制总结为下表：

### 预训练任务核心机制拆解

| 预训练任务               | 1. 输入被遮挡了什么？                                        | 2. 损失如何计算？                                            | 3. 监督的是哪个维度？                                        |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **MLM** (掩码语言建模)   | **遮挡文本 Token**： 随机遮挡 30% 的文本 Token（替换为 `[MASK]`）。  *注意：被遮挡词的 2D 布局坐标（BBox）和对应的视觉 Patch 完全保留。* | **多分类交叉熵损失 (Cross-Entropy Loss)**： 计算模型预测出的词汇概率分布与真实 Text Token ID 之间的差异。 | **单模态为主（文本）**： 监督模型在给定布局和视觉上下文的情况下，对**文本语义**的理解与重建能力。 |
| **MIM** (掩码图像建模)   | **遮挡图像 Patch**： 采用块状掩码（Blockwise Masking），随机遮挡约 40% 的图像 Patch（替换为 `[MASK]` 向量）。  *注意：文本和 BBox 信息全部保留。* | **多分类交叉熵损失 (Cross-Entropy Loss)**： 目标不是重建 RGB 像素，而是预测被遮挡区域对应的**离散视觉 Token ID**（由预训练的视觉离散分词器生成，类别数通常为 8192）。 | **单模态为主（视觉）**： 监督模型在给定文本提示和周围图像的情况下，对**视觉特征**的理解与重建能力。 |
| **WPA** (词与图像块对齐) | **不产生新的遮挡**： 直接复用 MIM 任务中产生的视觉 Patch 遮挡状态。 | **二元交叉熵损失 (Binary Cross-Entropy Loss)**： 对每一个**未被遮挡的文本 Token**进行二分类判别： • `1 (Aligned)`: 对应的 Patch 未被遮挡 • `0 (Unaligned)`: 对应的 Patch 被遮挡 | **跨模态对齐（核心）**： 显式监督**文本与视觉之间的细粒度空间对齐**，强制注意力机制学习坐标映射。 |

### 总体损失函数 (Total Loss)

在预训练的每一次前向传播中，模型的总损失是这三个任务损失的加权和（通常权重为 1:1:1）：

L=LMLM+LMIM+LWPA

### 总结

LayoutLMv3 的预训练设计是一个“三管齐下”的精妙系统：

1. **MLM** 保证了模型能读懂字（文本监督）。
2. **MIM** 保证了模型能看懂图（视觉监督）。
3. **WPA** 作为粘合剂，确保模型知道“哪个字对应图上的哪块区域”（跨模态对齐监督）。

这三者共同作用，才使得单流架构的 Transformer 能够在内部隐式地建立起强大的图文布局关联。

# LayoutLMv3对本课题的启发

## 1. 论文基本信息

- **任务：** 多模态文档理解（Multimodal Document AI / Document Understanding）。
- **发表时间：** 2022 年（ACM Multimedia 2022 接收）。
- **主要贡献：** 提出了首个彻底摒弃 CNN 的统一多模态文档预训练架构；引入了块状掩码图像建模（MIM）和词-块对齐（WPA）任务；在多项文档分类、抽取和问答基准测试中达到 SOTA。

## 2. 输入与输出

- **文本输入：** 经 OCR 提取的文本词汇（Tokens），及一维阅读顺序。
- **图像输入：** 统一缩放至固定分辨率（如 224×224）的文档全局图片。
- **布局输入：** OCR 文本对应的片段级（Segment-level）二维物理边界框（BBox）。
- **输出任务：** 为下游任务提供融合后的多模态隐向量序列，用于序列标注（信息抽取）、分类或抽取式起止点预测（DocVQA）。

## 3. 模型结构

- **OCR token 表示：** `词嵌入` + `1D阅读顺序位置编码` + `2D空间位置编码` + `Segment/Modality类型编码`，逐元素相加。
- **图像 patch 表示：** 借用 ViT 思想，将图片切分为 16×16 的固定网格（共 196 个 Patch），经线性投影拉平并加上 1D 图像位置编码。
- **bbox 表示：** 将连续坐标归一化并离散化至 `[0, 1000]` 的整数区间，计算宽 (w) 和高 (h)。分别在 X 轴和 Y 轴的 Embedding 表中查询，组合成 6 个特征向量的加和/拼接。
- **多模态融合方式：** 单流早期融合（Single-stream Early Fusion），文本 Token 和图像 Patch 直接拼接组成长序列。
- **Transformer 类型：** 单流共享参数的 Transformer Encoder（文本与视觉计算全局交叉注意力）。

## 4. 预训练任务

### MLM (Masked Language Modeling)

- **输入：** 随机遮挡 30% 的文本 Token，但**保留对应的 BBox 坐标和视觉 Patch**。
- **目标：** 结合上下文和视觉区域，预测被遮挡位置的真实 Text Token ID。
- **损失：** 多分类交叉熵损失。

### MIM (Masked Image Modeling)

- **输入：** 采用块状掩码（Blockwise）随机遮挡约 40% 的图像 Patch，**保留所有文本和 BBox 信息**。
- **目标：** 预测被遮挡区域对应的离散视觉 Token ID（由外部预训练的离散视觉分词器生成，非原始 RGB 像素）。
- **损失：** 多分类交叉熵损失。

### WPA (Word-Patch Alignment)

- **对齐对象：** 未被遮挡的文本 Token 与其空间上对应的图像 Patch。
- **正负样本：** 正样本（1 = 对应 Patch 未被遮挡），负样本（0 = 对应 Patch 在 MIM 任务中已被替换为 Mask 向量）。
- **损失：** 二元交叉熵分类损失（BCE Loss）。
- **学到的能力：** 显式的跨模态细粒度空间对齐，强制模型的注意力矩阵建立坐标位置与视觉特征的映射关系。

## 5. 下游实验

- **数据集：** RVL-CDIP（文档分类）、FUNSD/CORD（表单/票据信息抽取）、DocVQA（文档视觉问答）。
- **基线：** LayoutLM/v2, RoBERTa, DocFormer 等。
- **主要结果：** 纯 Transformer 架构全面超越依赖“CNN + 文本”双流特征提取的复杂基线模型。
- **消融结果：** MLM, MIM, WPA 缺一不可。片段级（Segment-level）的 BBox 编码表现优于甚至持平细粒度的词级别（Word-level）编码。
- **失败案例：** 论文未过多提及，但工程实践表明，由于将文档粗暴压缩为 196 个 Patch，在面对密集型长文档或细小表格数字时，纯视觉特征容易糊化丢失。

## 6. 与 ColPali 的关系

- **相同点：** 均摒弃了传统的 CNN 骨干，证明了直接使用“基于 Patch 的纯视觉特征序列”处理文档的高效性与可行性。
- **不同点：** LayoutLMv3 是深耦合的**单流跨模态架构（Cross-Encoder）**；ColPali 是独立的**纯视觉双塔晚期交互（Late Interaction / MaxSim）**。
- **LayoutLMv3 是否直接解决页面检索：** 否。由于序列拼接计算复杂度极高，无法在海量文档库中做到离线缓存与快速召回。
- **LayoutLMv3 是否直接解决区域检索：** 否。输出仍为 Token/Patch 级，缺乏直接针对“候选 Region”进行打分和排序的机制。

## 7. 可迁移模块 (用于毕业论文)

- **bbox/二维位置编码：** 将离散坐标解耦为 X/Y 轴分别查表映射的设计，可以直接搬到论文阶段二的“结构编码模块”中，为纯视觉 Region 赋予空间感知能力。
- **patch-region 对齐：** LayoutLMv3 证明了“同一片段共享 BBox”是有效的。这从侧面支撑了你“用一个大 BBox 将多个视觉 Patch 聚合为一个 Region 向量”的合理性，降低了对像素级精细对齐的依赖。
- **OCR-视觉对齐：** WPA 任务的二分类判别思想非常精妙。在阶段四如果引入训练，可以抛弃昂贵的生成式掩码，转而采用判别式对比损失（在一页中的候选 BBox 中选出正确的 Region）。
- **其他：** 坐标归一化（0-1000 离散化）预处理策略。

## 8. 不宜直接照搬的部分

- **任务差异：** 生成式的预训练（MLM/MIM）旨在全面理解，而你的任务核心是“检索排序与定位”，应专注于对比学习（Contrastive Learning）。
- **所需标注：** 从头进行类似 MLM/MIM 的训练需要百万级别的文档图像，在 MMDocIR 这种专门的检索集上强行做此训练容易过拟合。
- **计算或输入差异：** 绝不能引入单流 Query-Document 拼接，这会彻底毁掉 ColPali `MaxSim` 机制带来的低延迟检索优势。必须坚持物理坐标硬对齐（如 RoI Align）。

## 9. 对 MMDocIR 的可验证问题

- 布局区域是否能改善 ColPali 页面排序？（验证 **H1 & H2**，测试引入 Region 特征后的 MRR 和 Recall）
- OCR token 与视觉 patch 对齐是否能改善表格问题？（验证 **H5**，即诊断纯视觉 Patch 是否对密集数据失效）
- 哪类区域最受益？（按标题、段落、图片、表格、跨栏等布局类型进行细粒度指标拆解分析）

## 10. 当前结论

- **已确认：** “纯视觉 Patch 基座 + 显式布局对齐”是一条极具前景的检索路线；LayoutLMv3 提供了顶级的坐标编码范式，但其单流架构无法直接用于高效检索。
- **尚不确定：** 物理硬对齐（Patch-to-Region）会使索引体积（存储量）膨胀多少；BBox 映射在处理 ColPali 高分辨率网格边界时的具体工程损失。
- **下一步实验：** 拉取 ColPali 开源权重，在 MMDocIR 上跑通零样本（Zero-shot）的页面级检索基线，进行第一轮错误诊断。
