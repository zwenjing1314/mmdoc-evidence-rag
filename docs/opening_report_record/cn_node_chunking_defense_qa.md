# 中文年报证据节点切分实现说明与答辩问答

## 一、这一步到底做了什么

开题实验中提到：

```text
20 份中文年报
5327 个页面
99304 个细粒度证据节点
```

这里的 `99304` 个节点不是人工逐条标出来的，也不是随意切出来的，而是代码根据 PDF 页面解析结果自动生成的。

它的基本逻辑是：

```text
PDF
-> 每一页 page
-> PyMuPDF 抽取页面文本块 blocks
-> 每个 block 生成 paragraph 或 table_block 节点
-> 对包含财务指标和数字的 block 额外抽取 table_row 节点
-> 写入 nodes.parquet
```

也就是说：

```text
page 是页级单位；
node 是页内更细的证据单位。
```

## 二、代码位置

核心代码在：

```text
src/mmdocrag/datasets/adapters.py
```

主要函数包括：

| 函数 | 作用 |
|---|---|
| `_extract_pdf_page_items` | 用 PyMuPDF 读取 PDF 页面文本和页面 block |
| `_build_cn_page_nodes` | 把一页转换成多个 evidence node |
| `_block_chunks` | 将 PyMuPDF blocks 转成候选文本块 |
| `_fallback_text_chunks` | 如果 block 失败，则按文本行回退切分 |
| `_metric_row_chunks` | 从文本块中识别财务指标行 |
| `_looks_like_table_block` | 判断文本块是否像表格块 |
| `_unit_candidates` | 提取页面中的“单位：元/万元/亿元”等单位候选 |

## 三、第一步：PDF 页面解析

代码入口是：

```python
_extract_pdf_page_items(path)
```

它使用：

```python
import fitz
```

也就是 PyMuPDF。

对每一页执行：

```python
page.get_text("text")
page.get_text("blocks")
```

其中：

| 方法 | 得到什么 |
|---|---|
| `page.get_text("text")` | 整页文本 |
| `page.get_text("blocks")` | 页面内文本块及其坐标 |

每个 block 会保存：

```text
text
bbox
```

其中 `bbox` 是 PyMuPDF 给出的页面坐标：

```text
[x0, y0, x1, y1]
```

这一步得到的是页面级结构：

```text
[
  {
    "text": "整页文本",
    "blocks": [
      {"text": "文本块1", "bbox": [...]},
      {"text": "文本块2", "bbox": [...]}
    ]
  }
]
```

## 四、第二步：页面转 evidence nodes

真正生成节点的函数是：

```python
_build_cn_page_nodes(...)
```

它对每个页面执行：

```text
raw_chunks = _block_chunks(blocks) or _fallback_text_chunks(text)
```

含义是：

1. 优先使用 PyMuPDF 的页面 block；
2. 如果 block 为空，再用整页文本按行切分作为回退方案。

当前中文年报实验中，实际结果是：

```text
pymupdf_block_metric_rows: 99304
text_fallback: 0
```

说明当前 99304 个节点全部来自 PyMuPDF block 解析和指标行扩展，没有使用 fallback。

## 五、第三步：节点类型如何判断

当前节点主要有三类：

```text
paragraph
table_block
table_row
```

当前数量：

| node_type | 数量 |
|---|---:|
| `paragraph` | 75481 |
| `table_block` | 22677 |
| `table_row` | 1146 |

## 1. paragraph

如果一个文本块不太像表格，也不包含明显财务指标，就标为：

```text
paragraph
```

例如：

```text
公司持续推进技术研发和市场拓展，报告期内经营情况保持稳定。
```

## 2. table_block

判断函数是：

```python
_looks_like_table_block(text)
```

规则是：

```python
numbers = NUMBER_PATTERN.findall(text)
return len(numbers) >= 3 or _contains_financial_keyword(text)
```

也就是说，如果一个文本块中：

1. 数字数量大于等于 3；或
2. 包含财务关键词；

就认为它像表格块，标为：

```text
table_block
```

例如：

```text
营业收入 233,432,768,960.43 343,176,440,712.96 -31.98%
```

## 3. table_row

`table_row` 是在 `table_block` 或普通 block 基础上额外抽出来的指标行。

识别函数是：

```python
_metric_row_chunks(text)
```

它会查找财务关键词：

```text
营业收入
归属于上市公司股东的净利润
经营活动产生的现金流量净额
研发投入
研发费用
资产总额
负债合计
```

如果某个 block 里出现这些关键词，并且关键词后面 360 个字符内有数字，就额外生成一个：

```text
table_row
```

这样做的原因是：年报财务表格通常包含很多行，单纯保留整个表格块会太粗，而财务问答最需要命中的是具体指标行。

## 六、第四步：节点 ID 如何生成

节点 ID 格式是：

```text
{page_id}_n001
{page_id}_n002
{page_id}_n003
```

例如：

```text
万科A：2025年年度报告_p10_n001
万科A：2025年年度报告_p10_n002
```

这里：

| 部分 | 含义 |
|---|---|
| `万科A：2025年年度报告` | 文档 ID |
| `_p10` | 第 10 页 |
| `_n001` | 该页第 1 个节点 |

这样设计的好处是：

1. 可以直接从 node_id 看出节点来自哪一页；
2. 每次重新 prepare 时，节点编号相对稳定；
3. 方便将 QA 标注中的 `evidence_pages` 映射到 `evidence_node_ids`。

## 七、第五步：节点中保存了什么信息

每个节点会写成 `EvidenceNode`。

主要字段包括：

| 字段 | 含义 |
|---|---|
| `node_id` | 节点 ID |
| `doc_id` | 所属文档 |
| `page_id` | 所属页面 |
| `node_type` | 节点类型 |
| `bbox` | 页面坐标 |
| `text` | 节点文本 |
| `reading_order` | 阅读顺序 |
| `source` | 数据来源 |
| `confidence` | 置信度 |
| `metadata` | 附加信息 |

metadata 中包括：

```text
chunk_method
page_index
unit_candidates
source_pdf
```

例如：

```text
chunk_method = pymupdf_block_metric_rows
unit_candidates = ["元", "万元"]
```

## 八、为什么是 99304 个节点

因为 20 份年报一共有：

```text
5327 个页面
```

每页通常包含多个 PyMuPDF 文本块。

每个文本块会生成一个：

```text
paragraph 或 table_block
```

如果某些文本块中包含财务指标和数字，还会额外生成：

```text
table_row
```

最终得到：

```text
75481 个 paragraph
22677 个 table_block
1146 个 table_row
合计 99304 个 nodes
```

平均每页约：

```text
99304 / 5327 ≈ 18.6 个节点
```

这个数量在年报 PDF 中是合理的，因为年报每页通常包含多个段落、表格块、页眉页脚、注释和财务表格行。

## 九、这是不是严格的表格结构识别

不是。

当前实现是：

```text
文本块级切分 + 财务指标行规则识别
```

不是完整的表格结构识别。

它没有恢复完整的：

```text
行列关系
跨行跨列
表头层级
单元格坐标
```

所以答辩时要说清楚：

```text
当前开题前实验中的 table_block 和 table_row 是基于 PDF 文本块和财务关键词规则得到的初步证据节点，不是完整表格结构解析。后续论文工作会进一步引入表格结构化解析和版面模型。
```

这样回答比较稳，不会被老师追问“你的表格识别模型在哪里”。

## 十、如果答辩被问到，怎么回答

下面整理一些可能被问到的问题和回答。

## Q1：99304 个节点是人工标注的吗？

不是。

回答：

```text
不是人工逐条标注的。99304 个节点是代码自动从 20 份中文年报 PDF 中解析和切分得到的。具体做法是使用 PyMuPDF 对每页 PDF 抽取文本和文本块，然后把每个页面文本块转换为 paragraph 或 table_block 节点；对于包含营业收入、净利润、现金流、研发投入、资产总额等财务关键词并且包含数字的文本块，再额外抽取 table_row 节点。人工主要参与的是 QA 标注修订，而不是逐条标注所有节点。
```

## Q2：为什么节点数量比页面数量多这么多？

回答：

```text
因为 page 是页级单位，而 node 是页内证据单位。一页年报通常包含多个段落、表格、页眉页脚、注释和财务数据行。项目会把一页拆成多个文本块，每个文本块作为一个候选证据节点；如果文本块中包含关键财务指标，还会额外生成表格行级节点。因此 5327 页最终生成 99304 个节点，平均每页约 18.6 个节点。
```

## Q3：paragraph、table_block、table_row 是怎么区分的？

回答：

```text
paragraph 是普通文本块；table_block 是包含多个数字或财务关键词的文本块；table_row 是从包含财务指标的文本块中额外抽取出来的指标行。具体规则是：如果一个文本块中数字数量大于等于 3，或者包含营业收入、净利润、现金流、研发投入、资产总额等财务关键词，就标为 table_block；如果财务关键词后面一定窗口内存在数字，则额外生成 table_row。
```

## Q4：这个 table_row 是真正的表格行吗？

回答：

```text
严格来说，它是基于 PDF 文本块和财务关键词规则抽取的“表格行级证据节点”，不是完整的表格结构识别结果。当前开题前实验的目标是先验证页面级检索到区域级证据定位的可行性，所以采用轻量规则抽取财务指标行。后续论文工作会继续引入更严格的表格结构解析，例如表格单元格、表头和行列关系恢复。
```

## Q5：为什么不用完整的 OCR 或表格识别模型？

回答：

```text
本文的研究重点不是从零改进 OCR 或表格识别模型，而是研究长文档中的多粒度证据组织、检索和可信生成。开题前实验优先使用 PyMuPDF 解析 PDF 原生文本和页面 block，保证流程轻量、可复现、可快速验证。后续如果需要更强表格结构信息，可以接入 Docling、PaddleOCR、MinerU 或表格结构识别工具作为解析增强模块。
```

## Q6：PyMuPDF 抽取的 block 可靠吗？

回答：

```text
PyMuPDF 对原生 PDF 文本抽取比较稳定，适合处理这类电子版中文年报。当前实验中 99304 个节点全部来自 PyMuPDF block 解析和指标行扩展，没有使用 fallback。它的优点是速度快、可复现、能提供文本和 bbox；不足是对复杂表格行列结构的恢复有限。因此本文在开题阶段把它作为基础解析工具，后续会记录解析失败案例，并考虑接入更强解析工具。
```

## Q7：如果 PDF 是扫描件怎么办？

回答：

```text
当前中文年报实验主要处理的是原生 PDF，所以 PyMuPDF 可以直接抽取文本。如果遇到扫描件，PyMuPDF 可能无法抽取有效文本，这时需要接入 OCR 工具，例如 PaddleOCR 或其他文档解析工具。本文后续会把 OCR 作为解析层的可替换模块，但 OCR 本身不是本文的主要创新点。
```

## Q8：节点切分会不会太碎？

回答：

```text
会存在这个风险。节点太粗会导致证据定位不准确，节点太碎会导致上下文不完整。因此当前实现采取折中方案：优先使用 PDF 页面 block 作为基本节点，不做固定长度暴力切分；同时对财务指标行额外生成 table_row，以提高数值问题的证据定位能力。后续可以通过实验比较不同粒度对 Recall、MRR 和 Region Hit 的影响。
```

## Q9：节点切分会不会把一个完整表格拆坏？

回答：

```text
有可能。当前方法不能保证完整恢复表格结构，它更像是把表格相关文本切成可检索证据块。开题前实验主要验证“从页面定位到证据块”这一路线是否可行。后续论文中会把表格结构化解析作为改进方向，例如保留表头、行列关系和单位继承关系。
```

## Q10：为什么要额外生成 table_row？

回答：

```text
年报问答中很多问题是财务指标型问题，例如营业收入、归母净利润、经营活动现金流、研发费用和资产总额。如果只保留整页或大表格块，检索到的证据仍然比较粗，不利于判断答案是否被具体证据支持。额外生成 table_row 可以让系统更容易命中“指标名 + 数值 + 单位”所在的局部证据，从而支撑后续可信性验证。
```

## Q11：为什么 Region Hit@5 不是很高？

回答：

```text
Region Hit@5 是比 Page Recall 更严格的指标。Page Recall 只要求找到正确页面，而 Region Hit 要求找到具体证据节点。当前节点切分还是基于文本块和规则的初步版本，没有使用完整表格结构识别，也没有使用强 embedding 模型，因此 Region Hit@5 达到 0.2000 说明方法已经能命中一部分细粒度证据，但仍有较大提升空间。这也正好说明后续研究有继续优化的必要。
```

## Q12：如果老师问“这个算创新吗”，怎么回答？

回答：

```text
单独的 PyMuPDF block 切分不是创新点，它是基础工程实现。本文的创新点不在于提出新的 PDF 解析模型，而在于把页面、段落、表格块和指标行统一组织成可检索、可定位、可验证的 evidence node，并在此基础上研究页面级粗召回和区域级细定位的协同检索方法。开题前这一步是为了验证证据节点表示和两阶段检索路线的可行性。
```

## Q13：如果老师问“这个多模态体现在哪里”，怎么回答？

回答：

```text
当前中文年报前期实验主要验证文本和版面结构基础上的多粒度证据检索，还没有完整引入视觉 embedding 或 VLM。因此我会把它定位为多模态长文档研究的第一阶段：先完成 PDF 页面、文本块、bbox、表格块和证据节点的结构化表示。后续会在这个证据节点体系上继续引入页面图像、区域图像和视觉检索模型，形成真正的文本-视觉融合检索。
```

## Q14：如果老师问“为什么不用固定长度 chunk”，怎么回答？

回答：

```text
固定长度 chunk 容易切断表格行、标题层级和上下文关系。年报里的关键证据经常以表格行或页面块形式出现，比如“营业收入 具体数值 单位”。因此我没有优先采用固定 token 长度切分，而是先利用 PDF 自身的页面 block 和财务指标规则生成证据节点，这样更符合文档原始结构，也更方便保留页码、bbox、节点类型和单位候选等元数据。
```

## Q15：如果老师问“怎么保证可复现”，怎么回答？

回答：

```text
节点生成流程是确定性的。输入是固定的 20 份 PDF，解析工具是 PyMuPDF，节点 ID 使用 page_id 加顺序编号，例如 p10_n001、p10_n002。运行 prepare 命令后会重新生成 documents、pages、nodes 和 queries 四张 parquet 表。当前实验也保留了配置文件、运行结果和评价指标，因此可以通过同一套命令复现。
```

复现命令：

```bash
uv run mdr prepare --dataset cn_annual_reports --limit-docs 20
```

如果现场只需要 1 分钟解释，可以这样说：

```text
这 99304 个节点是通过代码自动切分得到的。具体来说，我用 PyMuPDF 对 20 份中文年报逐页解析，获取每页的原始文本和页面文本块。每个页面文本块会根据内容被转换成 paragraph 或 table_block 节点；如果文本块中包含营业收入、归母净利润、现金流、研发投入、资产总额等财务指标，并且附近存在数值，就额外抽取为 table_row 节点。每个节点都保存 node_id、doc_id、page_id、node_type、bbox、text、reading_order 和 metadata。最终 5327 页生成了 99304 个节点，其中 paragraph 75481 个、table_block 22677 个、table_row 1146 个。当前这一步是轻量级证据节点构建，不是完整表格结构识别，后续会进一步引入更强的表格解析和视觉检索模型。
```

应该说：

```text
这是多模态长文档研究的第一阶段，目前主要利用文本、页面结构和 bbox 信息，后续会继续引入页面图像和视觉检索。
```

不要说：


应该说：

```text
当前节点切分已经能支撑初步检索实验，但仍存在表格结构不完整和节点粒度需要优化的问题，这也是后续研究改进方向。
```
